## ۷. T-1 — `UNIQUE(supersedes_approval_id)`

**سؤال:** آیا هر Approval حداکثر توسط **یک** Approval جدید قابل supersede است؟

**شواهد Repository:**

- سند طراحی `docs/V1.8_DETAILED_SCHEMA_DESIGN.md` §۴.۳ (خط ۳۸۰) این را **صریحاً** ثبت کرده:
  > «یادداشت فنی باز (**نیازمند تصمیم کسب‌وکاری نیست**) … جلوگیری از این حالت نیازمند `UNIQUE` روی `supersedes_approval_id` است. **این Constraint در این مرحله اعمال نشد** (خارج از تصمیمات Owner).»
- `StageProgressApprovalService::supersede()` با گرفتن **قفل والد** و بررسی `pendingQuery()`، دو supersede **همزمان** روی یک ردیف را می‌بندد.
- اما مسیر زیر بسته **نیست**: ردیف A (approved) → supersede → B ساخته می‌شود → B تأیید می‌شود → **supersede دوبارهٔ A** → C ساخته می‌شود. حال A **دو جانشین** دارد (B و C) و هر دو شمرده می‌شوند ⇒ دوباره‌شماری سقف.

**طبقه‌بندی:** `technical hardening` — نه تصمیم کسب‌وکاری. سند طراحی خودش این را تأیید کرده است.

**تصمیم این فاز:**

```text
ACCEPTED AS-IS  (وضعیت فعلی حفظ شد)
```

دلیل: خواستهٔ صریح فاز این بود که در صورت technical بودن، **فقط به‌عنوان recommendation ثبت شود**. اعمال آن نیازمند مهاجرت جدید (`M-10`) است که زنجیرهٔ ۹-مهاجرتی اثبات‌شده و توپولوژی Batch تأییدشده را تغییر می‌دهد؛ این کار باید در یک Batch/گیت مجزا انجام شود.

```text
RECOMMENDATION — NOT APPROVED
```

| مورد | پیشنهاد |
|---|---|
| Constraint | `ALTER TABLE stage_progress_approvals ADD CONSTRAINT uq_spa_supersedes UNIQUE (supersedes_approval_id);` |
| جایگزینی | تنها `idx_spa_supersedes` (non-unique) فعلی حفظ می‌شود |
| ابطال در سطح کد | `assertNotSuperseded()` در مسیر `supersede()` نیز بررسی شود که `$source` خودش قبلاً supersede نشده باشد |
| فاز پیشنهادی | یک Batch مستقل پس از این Production Migration |

**ریسک فعلی:** پایین ولی واقعی — فقط از مسیر UI «اصلاح یک ردیف تاریخی» قابل触发 است، و `UNIQUE` روی ستون NULL-پذیر، رفتار موجود را برای همهٔ حالتهای سالم تغییر نمی‌دهد.
