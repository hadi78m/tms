## ۰. قاعدهٔ بنیادی — Review ≠ Execution

```text
Migration Review        = بازبینی مستندات طراحی و تأیید ورودی‌ها   ← این سند
Migration Design        = نوشتن فایل‌های Migration (بدون اجرا)      ← پس از تأیید Review
Migration Implementation = اجرای Migration روی PostgreSQL            ← پس از تأیید جداگانه
```

**این چک‌لیست هیچ Migrationی ایجاد نمی‌کند، هیچ SQLی اجرا نمی‌کند و هیچ داده‌ای را تغییر نمی‌دهد.**

> **شرط شروع این مرحله (تصمیم مالک پروژه):** Migration Review باید **پس از آماده‌شدن PostgreSQL** انجام شود.
> اگر محور Environment بسته نشده باشد، Review می‌تواند در چهار محور دیگر پیش برود، اما **نتیجهٔ نهایی آن مشروط به بسته‌شدن محیط است** و **هیچ Migrationی پیش از آن نوشته یا اجرا نمی‌شود.**

**بندهایی که `APPROVED` شدند (نمونهٔ شواهد):** ۱۴ CHECK تک‌ردیفی در PostgreSQL معتبر · ۱۲ FK همگی `RESTRICT` و با پوشش Index · ترتیب ۹ Migration از نظر FK صحیح · ۹ `stage_code` با جمع دقیقاً ۱۰۰ · مدیریت درست `NULL` در `UNIQUE (project_id, code)` · ایمنی Backfill `task_type = 'development'` (۳ تسک موجود، همه توسعه‌ای، `tasks_weight_null = 0`) · طبقه‌بندی Legacy (`wbs_phases.weight` صفر خواننده/تست).

**بندهایی که `ISSUE` بودند و اکنون رفع شده‌اند:** `aggregate constraints` (§۶) → راهبرد سه‌الزامی + Trigger تجمعی DEFERRED · `audit requirements` (§۸) → نگاشت `metadata` + `document_uploaded` · `cumulative approved ≤ allocated` → قفل والد Stage + Active Approval · محیط → PASS.

> ⛔ در این اجرا **هیچ Migration، Model، Service، Controller، Blade، Test یا Seeder ایجاد/تغییر نکرد** و **هیچ Schema Mutation یا تغییر داده** انجام نشد. همهٔ بررسی‌های دیتابیس `SELECT` روی `information_schema`/`pg_database` و فرمان‌های خواندنی Laravel بودند.

### ۶.۳ شرط ورود به Migration Design

هیچ فایل Migrationی نوشته نمی‌شود مگر:
1. هر پنج محور بالا `APPROVED` شوند (یا `DEFERRED` با تصمیم صریح کتبی)، **و**
2. پنج تصمیم ساختاری باز (§۱.۱) پاسخ بگیرند، **و**
3. محور Environment واقعاً بسته شود.

**وضعیت این سه شرط پس از بستن تصمیمات (۱۴۰۵/۰۶/۳۱):**

```text

```
