## 3. Audit Naming Convention (موجود)

رویدادهای فعلی Task: `task_created` · `task_updated_sensitive_field` · `task_submitted_for_review` · `task_status_changed` (با metadata.reason) · `task_dependency_added/removed` · `task_assigned/unassigned` · `task_approval_recorded` · `task_final_approved`.

## 4. DEC-040 Interaction Analysis

| پرسش | یافته |
|---|---|
| آیا گزارش‌های فعلی تغییر می‌کنند؟ | خیر — DEC-040 قاعدهٔ *نمایش* است؛ نویسندهٔ جدید فقط ورودی تجمیع را تغییر می‌دهد (stageدارها وارد گزارش می‌شوند). |
| Historical reporting؟ | بدون backfill هیچ ردیف تاریخی تغییر نمی‌کند؛ گزارش گذشته ثابت می‌ماند. |
| Task بدون stage مجاز است؟ | طبق `BD-02`/`OQ-04=2B` بله — هر گزینه‌ای که NULL را ممنوع کند نیازمند تصمیم مالک (DEC جدید) و خلاف تصمیم فعلی schema است. |
| Stage اجباری شود؟ | فعلاً خیر (DEC-013/Q4-2B) — الزام = DEC جدید. |
| Backfill لازم؟ | **تصمیم مالک** — بدون دستور، هیچ backfill انجام/طراحی نمی‌شود. |

## 5. Risks Specific to This Capability

* `chk_tasks_module_consistency` فقط `module_id IS NOT NULL` را چک می‌کند؛ انسجام `module_id = stage.module_id` cross-table است — باید در سرویس با خواندن از خود Stage تضمین شود (الگوی `DEC-021`).
* FK RESTRICT: stage قابل حذف نیست (کاتالوگ ثابت) — ریسک orphan صفر.
* گزارش DEC-040 پس از شروع assignment «به‌مرور پرتر» می‌شود — رفتار درست است ولی باید در docstring/label شفاف بماند.
