## 1. Current State

Task authorization in V1.10/V1.11 is a **layered, role-middleware + service-guard system** built across
DEC-042/043/044/045. It contains **no Laravel Policy** for Task and **no Gate::define/Gate::before** anywhere
(verified by search). ProjectScopeService (V11-01) exists but is consumed by nothing outside its own test suite.

Key structural facts (file-verified):
- `routes/web.php` — all task routes are inside `Route::middleware('auth')`; write routes carry `role:` middleware.
- `TaskController` — 6 of 9 methods duplicate the **contractor isolation check inline** (`$user->contractor_id && $task->contractor_id !== $user->contractor_id` → `abort(403)`).
- `TaskScopeService` (`app/Domain/Rules/TaskScopeService.php`) — the **canonical contractor scope** (`assertCanAccess`), used by `TaskAssignmentService` only. Two of its methods are empty stubs (`assertCanActAsAssignedContractor`, `assertCanManageContract` — Phase S1 placeholders).
- `TaskService::authorizeStageAssignment()` — supervisor-only service guard (DEC-042/044 Hybrid).
- `TaskAssignmentService` — canonical assignment writer with contractor-scope pre-check on the **assignee**, race mapping, SLA hooks.
- `ProjectScopeService` (V11-01) — single canonical source of Project Scope; supervisor = active membership, admin/management unrestricted, PM/viewer/others = `null` (Q1 preserve).
- **Permission catalog = 11 Spatie permissions** (`InitialTmsSeeder:19-23`); task-relevant: `create tasks`, `assign tasks`. Role→permission: PM = `create tasks` + `assign tasks`; supervisor has NO task permission (only `technical_approval`, `submit rework`, `view reports`).
- **No permission checks run for task routes** — enforcement is role-based (middleware) + contractor isolation + service guards. The `assign tasks` permission exists in the catalog but is never consulted.

## 6. Existing Role Enforcement
(§5 search: `role:`, `->can(`, `authorize(`, `Gate::`, `Policy`, `hasRole`, `hasAnyRole` — task-relevant hits only.)

- Coarse role gates: `role:admin|project_manager|supervisor|employer` (create/store, assign), `role:supervisor` (stage).
- Read routes (`index`, `show`, `start`, `submit`, dependencies) have **no role gate** — open to all 7 roles + any new role.
- `@can('technical_approval')`, `@can('final_approval')` in `tasks/show.blade.php` (real Gate permissions, not policies).
- Blade `hasRole` checks: `tasks/create.blade.php` (supervisor stage dropdown), `tasks/show.blade.php` (PM/admin sections).
- `AssignTaskRequest::authorize()` — contractor isolation only (returns true otherwise).
- **No `->can('create tasks')` / `->can('assign tasks')` anywhere** — permissions exist in catalog only.

## 7. Existing Permission Enforcement — NONE for tasks
Catalog (11 permissions, `InitialTmsSeeder:19-38`): role→permission mapping gives PM = `create tasks`+`assign tasks`; supervisor/employer/contractor get **no** task permissions. Enforcement today is purely role-middleware, so the permission layer is catalog-drifted from practice. Connecting it is **DR-TASK-01**.

## 8. Existing Contractor Scope
- Canonical: `TaskScopeService::assertCanAccess(task, actor)` — throws `ContractorScopeViolationException`.
- Contractor identity: `users.contractor_id` (nullable FK). Contractor user ⇔ non-null `contractor_id`.
- Query filter: `tasks.index` `whereHas('project', contractor_id)`.
- **Preserved**: TaskPolicy will NOT duplicate contractor logic; the service path keeps `TaskScopeService` (assignment); controller-inline duplicates migrate to Policy only where they are *resource* checks (see §9/§11 boundary).
- DEC-051 (Contractor Dimension) remains **BLOCKED** — no contractor business rule is proposed.

## 9. Project Scope Integration (§8)
- **Canonical relation: `tasks.project_id` (direct FK)** — no traversal needed. `Task→Module→Project` (`module_id` denormalized, DEC-021, not source of truth) and `Task→WbsPhase→Module→Project` exist but are auxiliary.
- TaskPolicy must call `ProjectScopeService::canAccessProject($task->project, $actor)` — **reuse, no re-implementation**.
- Retrieval (§13): `tasks.index` should gain `ProjectScopeService::applyProjectScope(Task::query(), $user)` (composable with the contractor `whereHas`). `DashboardController` and `AuditController` are **UNTOUCHED** in Phase 1 (previous Design Gate explicitly left reports/audit/dashboard for later; no evidence to change them now).

## 11. Policy / Middleware / Service Guard Boundary

```
Route Middleware      = coarse area/role access (unchanged: role:... gates)
FormRequest           = input validation (StoreTaskRequest etc.; authorize() may delegate to policy)
TaskPolicy            = resource authorization = Permission (where one exists) AND Project Scope
ProjectScopeService   = single canonical Project Scope source (V11-01, reused — no duplication)
TaskScopeService      = contractor scope service guard (UNCHANGED; assignment path)
TaskService /         = business invariants: state machine, stage-lock, same-project deps,
TaskAssignmentService   supervisor-only stage role, race mapping, audit
```

- Policy never duplicates state/stage/role invariants → those stay in services (D).
- Permission cannot bypass Project Scope: policy = `permission AND scope`.
- Permission cannot bypass business invariants: services re-check roles/states regardless of policy outcome (DEC-044 Hybrid preserved).

## 13. Task Assignment authorization (§12)
- Who can assign: today `role:admin|pm|supervisor|employer` middleware. Note: **supervisor and employer have no `assign tasks` permission** in the catalog — the middleware is broader than the permission catalog intends.
- Reassignment = same endpoint (service handles end-previous + new, idempotent same-user no-op).
- TaskPolicy alone is NOT sufficient for assignment: `TaskAssignmentService` also enforces contractor scope **on the assignee** (`assertCanAccess($task, $assignee)`) — a rule about the *subject* user, not the *actor* → stays in the Service Guard.
- Project scope must be enforced **before** assignment (Policy `assign` ability) — currently missing entirely.

## 14. HTTP Authorization Flow (proposed, §14)
```
Route Middleware (role:…) → FormRequest (validation; authorize() may call $this->authorize(...))
  → TaskPolicy (permission AND project scope) → Controller → Domain Service (invariants) → DB
```
Error semantics (§15, current, unchanged): Permission/Policy deny → 403 `AuthorizationException`; inline contractor/audit aborts → 403; business invariant → redirect-with-error or domain exception (`UnauthorizedTaskOperationException`, `TaskBlockedException`, `ContractorScopeViolationException`). No new exceptions in Phase 1.

## 18. Decision Requests (Owner) — §19

### DR-TASK-01 — Connect the `create tasks` / `assign tasks` permissions to TaskPolicy?
- **Issue:** Permissions exist in catalog but are never consulted; enforcement is role-middleware only. Connecting them changes who can act: supervisor and employer currently pass `role:admin|pm|supervisor|employer` on `tasks.assign` but hold **no** `assign tasks` permission.
- **Evidence:** `InitialTmsSeeder:19-38` (catalog + role→permission), `routes/web.php:44-48` (middleware), no `->can()` usage for tasks.
- **Options:**
  - **(A) Connect both permissions in Policy** (policy = permission AND scope): supervisor/employer lose assign/create unless granted. Strict catalog alignment; **breaking** for supervisor/employer assignment flow.
  - **(B) Permission as additional layer where catalog intends it, roles keep working** (policy = (permission OR role-based) AND scope): no breaking change; catalog drift persists.
  - **(C) Defer permission enforcement to a later phase** (Phase 1 = scope only): no breaking change; smallest step; permission layer stays drifted.
- **Consequences:** (A) aligns catalog but breaks supervisor/employer assignment until catalog/roles change (catalog change = Owner decision); (B) preserves behavior, keeps drift; (C) keeps Phase 1 minimal and purely additive.

### DR-TASK-02 — Apply Project Scope to PM / employer / admin-adjacent roles on tasks?
- **Issue:** Q1 (V11-01) locked: PM/viewer get **no** project scope derived (`accessibleProjectIds` = null = unrestricted at the project-scope layer). If TaskPolicy applies scope, PM/employer/viewer remain unrestricted — meaning Phase 1 scope only restricts supervisors. Is that the intended behavior, or should PM scope also derive from something new (invented rule — requires Owner decision)?
- **Evidence:** `ProjectScopeService::accessibleProjectIds()` (V11-01, Q1 locked), DR-11-1 record.
- **Options:**
  - **(A) Q1-compliant: scope applies to supervisors only** (PM/employer/viewer unrestricted). No new business rule; consistent with locked decision; cross-project supervisor leak is closed — the actual V1.11 goal.
  - **B: extend scope derivation for PM/employer** — requires inventing a source (assignment? contract? none exists in repo) → violates "no invented business rule" unless Owner explicitly defines the basis.
- **Consequences:** (A) minimal, decision-consistent, closes the supervisor cross-project hole; (B) needs a data model the repo does not have.
