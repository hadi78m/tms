# سامانه مدیریت وظایف پروژه‌ها و قراردادهای پیمانکاری

## نام پروژه

Task Management System (TMS)

## هدف اصلی

ساخت یک سامانه مستقل برای مدیریت، کنترل و ارزیابی وظایف پروژه‌ها و قراردادهای پیمانکاری و پشتیبانی.

این سامانه باید وضعیت واقعی اجرای کار، میزان پیشرفت، نتیجه فعالیت‌ها، تأییدها، تأخیرها و عملکرد پیمانکار را به‌صورت شفاف مدیریت کند.

هدف نهایی این است که ارزیابی عملکرد پیمانکار و پرداخت‌های مرتبط با قرارداد، تا حد امکان بر اساس عملکرد واقعی و تأییدشده انجام شود.

---

## ارتباط با سامانه اصلی

سامانه اصلی سازمان دارای اطلاعات زیر است:

* قراردادها
* پیمانکاران
* سامانه‌های سازمان

TMS باید اطلاعات مورد نیاز خود را از سامانه اصلی دریافت کند.

روش اتصال هنوز باید نهایی شود:

1. API
2. دیتابیس مشترک

TMS نباید اطلاعات اصلی قرارداد، پیمانکار و سامانه را بدون دلیل در یک ساختار مستقل و متناقض بازتعریف کند.

## تصمیم‌های قطعی کسب‌وکار

1. هر Task به یک قرارداد مشخص وابسته است.
2. هر قرارداد با یک پیمانکار و یک سامانه مرتبط است.
3. پیمانکار اجازه ایجاد Task ندارد.
4. Task می‌تواند Subtask داشته باشد.
5. Task می‌تواند وابستگی داشته باشد.
6. وزن Task یا مرحله باید از ابتدا مشخص شود.
7. وزن‌دهی بر اساس نفرساعت پیمانکار انجام نمی‌شود.
8. WBS برای تعیین مراحل، خروجی مورد انتظار و مدت اجرای هر مرحله استفاده می‌شود.
9. WBS الزاماً به Gantt Chart تبدیل نمی‌شود.
10. بهره‌بردار می‌تواند در صورت نیاز Taskهای مشخص را تعریف کند.
11. بهره‌بردار مسئول اصلی بررسی و تأیید نتیجه کار است.
12. ناظر مسئول بررسی، نظارت و اعلام نظر تخصصی است.
13. پیمانکار کاربر مستقیم سامانه نیست؛ مگر در آینده تصمیم دیگری اتخاذ شود.
14. سیستم برای تعریف RFP یا Scope پروژه ساخته نمی‌شود.
15. پرداخت پشتیبانی نباید صرفاً بر اساس تقسیم مبلغ قرارداد بر ۱۲ انجام شود.
16. ارزیابی عملکرد باید بر اساس نتیجه و تأیید واقعی کار انجام شود.
17. SLA و تأخیر وظایف باید قابل ثبت، کنترل و گزارش‌گیری باشند.
18. دیتابیس TMS باید از صفر و متناسب با نیازهای خودش طراحی شود و نباید Schema دیتابیس سامانه اصلی کپی شود.

## نقش‌های احتمالی کاربران

* مدیر سیستم
* مدیر قرارداد
* بهره‌بردار
* ناظر پروژه
* مدیر ارشد / مشاهده‌گر گزارش‌ها

این نقش‌ها فعلاً مفهومی هستند و هنوز نباید به Role و Permission واقعی تبدیل شوند.

---

## گردش کار مفهومی Task

Draft
→ Assigned
→ In Progress
→ Submitted
→ Under Review
→ Approved / Rejected

این گردش کار هنوز باید در مرحله طراحی نهایی بررسی شود.

---

## اصول طراحی

* سادگی در شروع پروژه
* جلوگیری از پیچیدگی غیرضروری
* تفکیک کامل نیازمندی‌های کسب‌وکار از پیاده‌سازی فنی
* جلوگیری از وابستگی به نفرساعت اعلامی پیمانکار
* ثبت تاریخچه تغییرات مهم
* قابل گزارش‌گیری بودن وضعیت پروژه و قرارداد
* امکان توسعه API در آینده
* حفظ قابلیت اتصال به سامانه اصلی
* عدم ایجاد قابلیت‌های خارج از محدوده پروژه بدون تأیید مالک سیستم
