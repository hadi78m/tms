## DR-11-1 — F-1 Project-Scope Authorization

**مسئله:** Supervisor/Employer/Management بدون هیچ project-scope به تسک‌های همهٔ پروژه‌ها دسترسی دارند. جدول `projects` ستون مالکیت ندارد و هیچ membership structure وجود ندارد → هر fix احتمالاً Migration لازم دارد.
**اثر:** ~۹ route (index/show/start/submit/dependencies/stage/approvals) + audit و reports.

### گزینه‌های مبنای scope
* **A — Assigned-projects:** کاربر فقط پروژه‌هایی را می‌بیند که صریحاً به او تخصیص یافته (نیازمند جدول membership یا `supervisor_id`/`employer_id` روی projects — Migration)
* **B — Org-wide (وضع موجود مستند):** رفتار فعلی عمدی اعلام و فقط با تست قفل شود (بدون Migration)
* **C — Contract-based:** scope از `contract`/`contractor` کاربر مشتق شود (بدون ساختار جدید برای supervisor؛ employer موجود)
* **D — ترکیبی نقش-محور:** employer=contract-based، supervisor=assigned، admin/management=unrestricted

### سؤالات تکمیلی برای Owner
1. آیا Admin/Management unrestricted می‌مانند؟
2. Enforcement کجا باشد؟ (route middleware / Policy / service guard — سازگار با DEC-044)
3. آیا Audit UI (DEC-045) هم scope می‌گیرد یا system-wide می‌ماند؟

## DR-11-2 — Policy Migration Scope (VF-1)

**مسئله:** هیچ کلاس Policy وجود ندارد؛ enforcement فعلی = role middleware + service guard (Hybrid عملی V1.10).

### گزینه‌ها
* **A — فقط Resourceهای جدید:** Policy فقط برای قابلیت‌های آینده
* **B — Task/Project ابتدا:** Policy برای پرترددترین resourceها، بقیه حفظ
* **C — تمام Resourceهای مجاز:** Task · Project · Module · ModuleStage · StageProgressApproval · WbsPhase · User
* **D — Gradual بر اساس Risk:** ترتیب بر اساس شدت gap (tasks → approvals → modules → wbs)

**یادداشت:** Policy = لایهٔ resource ACL؛ Service Guardها برای invariants حفظ می‌شوند (DEC-044 پابرجا). Migration: NO (فقط کد). Rollback: آسان.

## DR-11-3 — Settings & Access Architecture

**مسئله:** ترجیح Owner: «Role و Access در تنظیمات و دسترسی‌ها قابل واگذاری باشند». وضع فعلی: roleها در کد هاردکد؛ admin فقط `syncRoles` دارد؛ `system_settings` فقط behavioral (۵ کلید، هیچ کلید access ندارد).

### سؤالات Owner
1. Role ثابت بماند یا قابل-تعریف از UI؟
2. Permission mapping (permission↔route/ability) از UI قابل ویرایش باشد؟
3. چه نقشی حق ویرایش Access دارد؟ (admin فقط؟ admin+management؟)
4. Delegation (supervisor→کاربر دیگر) لازم است؟
5. کدام Business Invariants هرگز از UI قابل Override نباشند؟ (پیشنهاد فهرست: SUM=100، ceiling، immutability، DEC-043 lock، DEC-040 rule، مرز مالی DEC-041)
6. Audit Visibility (DEC-045) در UI قابل تغییر باشد یا DEC-locked؟

**هشدار معماری:** dynamic mapping کامل = Migration + بازبینی ۵۲ مسیر؛ درvariants باید همیشه در service guard بمانند.

## DR-11-4 — OQ-32 Contractor Dimension

**مسئله:** `stage_progress_approvals` بُعد contractor ندارد؛ `performance_records` خودکار به approvals متصل نیست.

### گزینه‌های dimension
* **A — Task-level:** aggregation از `tasks.contractor_id` (بدون ستون جدید روی approvals؛ قاعدهٔ snapshot لازم)
* **B — Stage-level:** contractor روی stage (ساختار جدید — کل stage به یک پیمکار)
* **C — Approval-level:** contractor روی هر approval row (دقیق‌ترین؛ Migration + قاعدهٔ ceiling-interaction)
* **D — موکول:** OQ-32 باز بماند

همهٔ A–C = Migration Candidate + Business Rule جدید (قاعدهٔ snapshot/aggregation).
