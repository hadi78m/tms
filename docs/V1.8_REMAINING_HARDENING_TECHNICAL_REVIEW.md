## PART 2 — T-1: UNIQUE(supersedes_approval_id)

### ۲.۱ وضعیت Database (Catalog — فقط-خواندنی)

```text
UNIQUE constraints (14 total) → هیچ‌کدام روی stage_progress_approvals.supersedes_approval_id نیست
Index موجود                   → idx_spa_supersedes (غیریکتا) — طبق M-03
CHECK                         → chk_spa_no_self_supersede (supersedes_approval_id <> id)
FK                            → ON DELETE RESTRICT (self-FK)
```

⇒ **دیتابیس به‌تنهایی فork را نمی‌بندد** — طبق انتظار (`ACCEPTED AS-IS`).

### ۲.۲ وضعیت Application Guard

| مسیر | گارد | خط |
|---|---|---|
| `supersede()` | `assertNotSuperseded($source)` | :249 |
| `adjust()` | `assertNotSuperseded($row)` | :100 |
| `approve()` | `assertNotSuperseded($row)` | :134 |
| `reject()` | `assertNotSuperseded($row)` | :200 |

`assertNotSuperseded()` (خط ۳۵۱) → `isSuperseded()` → `EXISTS(supersedes_approval_id = id)` ⇒ **هر ۴ مسیر تغییری، در ابتدای تراکنش، ردیف‌های تاریخ را می‌بندند** — `supersede()` روی `$source` (نه روی `$successor`).

### ۲.۳ پاسخ به سناریوی Fork

سناریو `A → B` سپس `A → C` وقتی `B` تصمیم‌گرفته شده:

1. `supersede(A) → C` → `lockStage` → `assertNotSuperseded(A)` → `isSuperseded(A)` = `EXISTS(supersedes_approval_id = A.id)` → **true** (B از قبل به A اشاره می‌کند) → `InvalidApprovalException`.
2. `approve(C)` هرگز اتفاق نمی‌افتد — C ساخته نمی‌شود.

⇒ **Application-level invariant بسته است** — همان نتیجهٔ ۱۶ تست زنجیرهٔ supersede.

### ۲.۴ رده‌بندی نهایی T-1

```text
T-1 = ACCEPTED AS-IS  (+ یک تصمیم مالک باز: آیا روزی M-10 ساخته شود یا خیر)
```

**چرا M-10 لازم می‌شود (اگر مالک بخواهد):** دیتابیس تضمین دائمی می‌خواهد، زیرا مسیرهای مستقیم از SQL خام (بدون Application) هنوز فork می‌کنند. Migration: `ALTER TABLE stage_progress_approvals ADD CONSTRAINT uq_spa_supersedes UNIQUE (supersedes_approval_id);` — یک Batch مستقل، بدون تأثیر بر رفتار سالم (column nullable). تا این تصمیم، گارد سطح Application کافی و تأییدشده است.

### ۲.۵ تست رگرسیون موجود

`tests/Feature/V18/StageProgressApprovalSupersedeChainTest.php` (۱۶ تست · ۵۵ assertion) — شامل `T1-00` (نگهبان مستنداتی فork)، `T1-03b` (سناریوی دقیق A→B سپس A→C) و `T1-07b` (حالت عددی که قبلاً بی‌صدا رد می‌شد).

## PART 3 — T-3: task_rejected Audit Event

### ۳.۱ جریان کامل رد تسک

| مسیر رد | مالک | رویداد ثبت‌شده |
|---|---|---|
| رد فنی (Supervisor، `under_review → needs_rework`) | `ApprovalService::recordTechnicalApproval()` :27 | `task_approval_recorded` |
| رد نهایی (Employer، `supervisor_approved → needs_rework`) | `ApprovalService::recordFinalApproval()` :75 | `task_approval_recorded` + `task_final_approved` |
| نیاز به اصلاح (Service عمومی) | `TaskService::needsRework()` :155 | `task_status_changed` + `reason` |
| رد درخواست تغییر وزن | `WeightChangeRequestService::rejectRequest()` | `task_weight_change_rejected` |
| رد Stage Progress (دامنهٔ V1.8) | `StageProgressApprovalService::reject()` :191 | `stage_progress_rejected` |

**نکته:** دو مسیر رد تسک (`recordTechnicalApproval` و `recordFinalApproval` با `ApprovalStatus::NeedsRework`) **هر دو** از `task_approval_recorded` استفاده می‌کنند — **هیچ مسیری گارد Audit را دور نمی‌زند**؛ فقط رویداد «اختصاصی رد» وجود ندارد.

### ۳.۲ پاسخ به پرسش‌های فاز

1. **آیا `task_rejected` توسط تصمیم موجود الزامی است؟** — **خیر.** جست‌وجوی کل `docs/` و `project_context/`: هیچ DEC یا BD ای وجود ندارد که رویداد اختصاصی رد را الزام کند. تنها مرجع، `M-5` در `V1.8_MIGRATION_REVIEW_REPORT.md` است که خودش می‌گوید «اگر مرجع کسب‌وکاری Task Rejection را رویداد مستقل بخواهد، فهرست §۸.۳ باید اصلاح شود» — یعنی **مرجع کسب‌وکاری لازم است، نه موجود.**
2. **نقص واقعی یا توصیهٔ گم‌شده؟** — **توصیهٔ گم‌شده، نه نقص.** رد در حال حاضر کاملاً Audit می‌شود (از طریق `task_approval_recorded` با `status = needs_rework` و `comment`/`reason` کامل) و `TaskService::needsRework()` رویداد با `reason` هم دارد. هیچ مسیر ردی بی‌سروصدا نیست.
3. **اگر روزی تأیید شود، از کجا صادر شود؟** — در `ApprovalService::recordTechnicalApproval()` و `recordFinalApproval()`، بلافاصله بعد از `$this->auditService->log('task_approval_recorded', ...)`، در همان `DB::transaction` — الگوی موجود: `if ($status === ApprovalStatus::NeedsRework->value) { log('task_rejected', ...) }`.
4. **پیاده‌سازی چه چیزی لازم دارد؟** — **فقط کد + تست**؛ **صفر Schema · صفر Migration · صفر Enum جدید** (event name یک رشتهٔ audit است، نه enum؛ رویدادها فهرست باز در `DatabaseAuditService` دارند).

### ۳.۳ رده‌بندی نهایی T-3


## PART 5 — T-5: Project Soft Delete

### ۵.۱ یافته‌های واقعی

| مورد | وضعیت |
|---|---|
| `Project` uses SoftDeletes? | ✅ بله (`use SoftDeletes` + `softDeletesTz()` در Migration — Baseline، Immutable) |
| چه کسانی به Project ارجاع دارند؟ | `tasks.project_id` · `modules.project_id` · `wbs_phases.project_id` — همه `ON DELETE RESTRICT` |
| FK behavior on **hard** delete | PostgreSQL `RESTRICT` → **مسدود** (صرف‌نظر از SoftDelete) |
| Soft-deleted project visible? | Eloquent: **نه** (Global scope خودکار SoftDeletes) — اما Raw SQL / DB-level: **بله** |
| Custom global scope? | ❌ هیچ — هیچ Model یک global scope دستی ندارد (`booted()` فقط در ActivityLog/Approval/SlaEvent/StageProgressApproval برای immutable guards است) |
| Restore → inconsistent state? | فقط اگر Modules/Checklist در فاصلهٔ حذف/بازگردانی اضافه شوند — اما **حذف نرم، فرزندان را حذف نمی‌کند**؛ همهٔ فرزندان باقی می‌مانند و صرفاً visible از Eloquent نیستند |

### ۵.۲ تحلیل ریسک

- **DB-level:** `RESTRICT` روی هر ۳ فرزند ⇒ hard delete مسدود است؛ حذف نرم، هیچ ردیف فرزندی را تغییر نمی‌دهد. **صفر ناسازگاری state**.
- **Application-level:** `ModuleService` و `ModuleStageService` به‌صورت ایمن با `SUM = 100` کار می‌کنند؛ اگر Project حذف نرم شود، `Project::modules()` خالی برمی‌گرداند ولی در DB موجودند. اگر restore شود، دقیقاً همان state قبلی بازمی‌گردد.
- **قاعدهٔ مشترک در DB مفقود است:** هیچ Trigger/CHECK ای وجود ندارد که "حذف نرم Project با Module Active" را ببندد. اما چون حذف نرم، محاسبات (`SUM`، `rebalance`) را در DB تغییر نمی‌دهد، **هیچ state ناسازگاری ساخته نمی‌شود**.

### ۵.۳ رده‌بندی نهایی T-5

```text
T-5 = STRUCTURAL RISK (پایین) — رفتار فعلی درست است؛ هیچ قاعدهٔ DB-level برای حذف نرمِ Project-with-Active-Modules مفقود است اما امروز هیچ آسیبی نمی‌زند
```

**نه** `already correct` (چون قاعدهٔ DB مفقود است) · **نه** `active defect` (چون صفر آسیب فعلی) · **نه** `owner decision required` (مگر اینکه مالک بخواهد قاعدهٔ "حذف نرم Project با Module فعال" را ببندد — آن‌گاه تصمیم کسب‌وکاری + Constraint Trigger جدید).
