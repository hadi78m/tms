## 4. DR-3 Options — Trade-off Tables (خنثی)

### Option A — Keep Current
* Scope: هیچ تغییر. · Pros: صفر ریسک regression؛ رفتار اثبات‌شده. · Cons: F-1..F-3 باقی می‌ماند؛ هر مسیر جدید الگو را تکرار می‌کند. · Security: بدون تغییر (نه بهتر، نه بدتر). · Regression risk: صفر. · Test impact: صفر. · Migration effort: صفر. · Rollback: n/a.

### Option B — Gradual Policy Migration
* Scope: Policy برای Module/Stage/StageApproval/WbsPhase (V1.9 resources) سپس Task. · Pros: مجوز resource-centred؛ Blade `@can` استاندارد؛ تست‌پذیری یکنواخت. · Cons: ۵۲ مسیر بازبینی؛ دوگانگی موقت بین نسلی؛ ریسک نگاشت نادرست ability→role. · Security: بهبود اگر F-2/F-3 در همان Policy بسته شود. · Regression risk: Medium. · Test impact: ارتقای TD-8 (هر route × نقش). · Migration effort: Medium (فقط کد). · Rollback: revert کد — آسان.

### Option C — Hybrid
* Scope: Policy برای resource-level (view/create/update) + حفظ گارد سرویس برای invariants (ceiling، mode، state machine). · Pros: جدایی مسئولیت invariant/authorization؛ کمترین دست‌خوردگی سرویس‌ها. · Cons: دو لایه باید مستند و هم‌راستا بمانند (اکنون هم هست ولی نامستند). · Security: مشابه B برای resource، بدون لمس سرویس. · Regression risk: Low–Medium. · Test impact: همان B. · Migration effort: Medium. · Rollback: آسان.

**Framework note (بدون استناد به‌عنوان تصمیم):** Laravel 13 از Policy برای `ability روی Model` پشتیبانی بومی دارد؛ انتخاب/عدم انتخاب آن، تصمیم مالک است.
