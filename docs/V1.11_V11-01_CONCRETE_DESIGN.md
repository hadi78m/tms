## 5) Final Membership Schema

### 5.1 جدول: `project_memberships`

نام جدول بر پایهٔ C-8 (جمع snake_case + مفهوم owner-approved «Project Membership / Assignment»). نام‌های ردشده: `project_supervisors` (M-2 — ناسازگار با M-1 تأییدشده)، `project_users` (بار معنایی pivot خام؛ concept membership را منتقل نمی‌کند).

| ستون | نوع | Null | کلاس | دلیل / شاهد |
|---|---|:-:|---|---|
| `id` | `id()` (bigserial) | — | **REQUIRED** | C-1 |
| `project_id` | `foreignId` → `projects.id` `onDelete('restrict')` | NOT NULL | **REQUIRED** | نیمهٔ Project رابطه؛ C-2 |
| `user_id` | `foreignId` → `users.id` `onDelete('restrict')` | NOT NULL | **REQUIRED** | نیمهٔ User رابطه؛ C-2 |
| `membership_type` | `string(50)` | NOT NULL | **REQUIRED** | **حامل predicate قید کاردینالیتی** (§5.2). C-7: بدون `CHECK IN (...)` |
| `started_at` | `timestampTz` | NOT NULL | **REQUIRED** | OD-6-b (لحظهٔ فعال شدن تخصیص؛ صفر آینده‌نگر ⇒ همیشه `now()`). قرینه: `task_assignments.assigned_at` |
| `ended_at` | `timestampTz` | NULL | **REQUIRED** | OD-6-a — **تنها** منبع حقیقت «فعال» |

| `reason` | `string(255)` | NULL | **OPTIONAL (recommended)** | قرینهٔ `task_assignments.reason` (nullable) + قابلیت ردیابیِ «چرا ناظر عوض شد». nullable ⇒ صفر قاعدهٔ جدید؛ عدم‌الزام به پر کردن |
| `created_at` | `timestampTz` `useCurrent()` | NOT NULL | **REQUIRED** | C-3 |

| ستون پیشنهادی | حکم | دلیل |
|---|---|---|

| `status` (فقط برای Active/Inactive) | **NOT NEEDED — ممنوع** | OD-6-a |

| `position` / `role` (ستون دوم) | **NOT NEEDED** | `membership_type` کافی است؛ واژهٔ `role` در این مخزن بار Spatie دارد و خطر اختلاط با DEC-050 |
| `project_role_permissions` (جدول دوم) | **NOT NEEDED** | M-3 رد شد (over-engineering؛ قرینه‌ای برای چندموقعیتی‌بودن نیست) |

### 5.2 نمایش «نوع تخصیص / Supervisor» — تصمیم قطعی

**انتخاب: گزینهٔ A — ستون `membership_type` روی همان جدول generic، با مقدار `supervisor`.**

دلایل (evidence-based، نه سلیقه):

1. **M-1 تأیید شده است** ⇒ ساختار generic لازم است؛ پس B (جدول نوع جدا) و C (رابطهٔ supervisor-specific) خارج می‌شوند.
2. **قید DB برای کاردینالیتی به یک discriminator نیاز دارد:** `UNIQUE (project_id) WHERE ended_at IS NULL AND membership_type = 'supervisor'`. بدون ستون نوع، predicate ایندکس **همهٔ** انواع عضویت را قفل می‌کند و مثلاً «دو Employer فعال» را هم ممنوع می‌کند — قاعده‌ای که مالک تصویب نکرده (Recon §4.3).
3. **سازگاری با C-7:** الگوی موجود مخزن برای «کد/نوع کنترلی» = `string(50)` بدون `CHECK IN` (`stage_code`، `task_type`، `status`) تا افزودن مقدار آینده Migration نخواهد.
4. **مرز DEC-050 حفظ می‌شود:** `membership_type` یک **برچسب عملیاتی scope** است، نه permission؛ هیچ نگاشت permission→route روی آن ساخته نمی‌شود.

**مقدار مجاز در V11-01: فقط `supervisor`.** (Employer در V11-01 ثبت نمی‌شود — OD-2.) مقدار به‌صورت enum PHP در `app/Domain/Enums/ProjectMembershipType.php` (الگوی `ModuleStatus`/`WbsPhaseCompletionStatus` در مخزن موجود است) نگهداری می‌شود، اما **نه** به‌عنوان enum cast روی Model (قرینهٔ مخزن: enum فقط برای `.value` استفاده می‌شود — `Module::scopeActive`). ⇒ صفر Migration برای افزودن نوع آینده.

### 6.1 قید تاریخ (K-4)

`ended_at >= started_at` یک **قاعدهٔ ساختاری** است، نه قاعدهٔ تجاری جدید (قرینهٔ `chk_ta_dates`). با OD-6-c (صفر تخصیص آینده‌نگر) هیچ ابهامی باقی نمی‌ماند: `started_at` همیشه لحظهٔ ثبت و `ended_at` همیشه لحظهٔ پایان دادن است.

### 6.2 قید «حداکثر یک Supervisor فعال» (K-6)

**معنای دقیق ایندکس:** به‌ازای هر `project_id`، **حداکثر یک** ردیف با `ended_at IS NULL` **و** `membership_type = 'supervisor'` مجاز است. ردیف‌های تاریخی (`ended_at IS NOT NULL`) **نامحدود**اند. هیچ نوع عضویت دیگری در V11-01 وجود ندارد؛ اگر در آینده اضافه شود، K-6 آن را محدود نمی‌کند (به‌عمد).

**چرا اعتبارسنجی برنامه‌ای تنها کافی نیست:**

1. الگوی خواندن–سپس–نوشتن در PostgreSQL با سطح پیش‌فرض `READ COMMITTED` دو تراکنش موازی را متوقف نمی‌کند: هر دو `SELECT` می‌کنند «تخصیص فعال وجود ندارد» و هر دو `INSERT` می‌کنند. تنها یک قید DB می‌تواند یکی را متوقف کند.
2. مخزن **قبلاً** همین ریسک را دیده و حل کرده است: `idx_active_assignment` + نگاشت `QueryException` به `TaskAssignmentRaceConditionException` (`TaskAssignmentService:98-103`).
3. K-6 تضمین‌کنندهٔ **ساختاری** است: حتی مهاجرت داده، اجرای دستی SQL، یا یک مسیر کد آینده نمی‌تواند دو ناظر فعال بسازد.

### 6.3 جریان جایگزینی و هم‌زمانی (طرح — پیاده‌سازی نمی‌شود)

```text
ProjectMembershipService::assignSupervisor(AssignProjectSupervisorData $data, User $actor):

  DB::transaction(function () {
      Project::where('id', $data->project_id)->lockForUpdate()->firstOrFail();     // parent lock (C-14)

      $active = ProjectMembership::where('project_id', ...)
                  ->where('membership_type', ProjectMembershipType::Supervisor->value)
                  ->whereNull('ended_at')
                  ->lockForUpdate()->first();                                       // row lock

      if ($active && $active->user_id === $data->user_id) { return $active; }       // idempotent no-op

      if ($active) {
          $active->ended_at = now(); $active->save();                               // پایان، نه حذف (OD-6-d)
          audit('project_supervisor_ended', $active, $actor, ['user_id' => $active->user_id], ['user_id' => null]);
      }

      $new = ProjectMembership::create([
          'project_id' => ..., 'user_id' => $data->user_id,
          'membership_type' => ProjectMembershipType::Supervisor->value,
          'started_at' => now(), 'ended_at' => null,
          'assigned_by' => $actor->id, 'reason' => $data->reason,
      ]);
      audit('project_supervisor_assigned', $new, $actor, [], ['user_id' => $new->user_id, 'reason' => $data->reason]);

      return $new;
  });
  // catch (QueryException) → اگر پیام شامل 'idx_active_project_supervisor' ⇒ throw ProjectMembershipRaceConditionException
```

نکات الزامی: ترتیب **پایان دادن قبل از ایجاد** (یک‌زمانیِ گذرا: در لحظهٔ `now()` ردیف قدیمی `ended_at = now()` دارد ⇒ دو ردیف فعال هم‌زمان **هرگز** وجود ندارد، حتی داخل تراکنش). نگاشت استثنا مطابق C-15.

## 7) Supervisor Cardinality

| مورد | طرح |
|---|---|
| معنا | حداکثر **یک** `project_memberships` با `(project_id, membership_type='supervisor', ended_at IS NULL)` |
| تضمین DB | K-6 (partial unique index) |
| تضمین برنامه | `ProjectMembershipService` (transaction + parent lock + row lock + idle idempotency) |
| تخصیص تاریخی | نامحدود (ردیف‌های `ended_at IS NOT NULL`) |
| جایگزینی | OD-6-d — پایان دادن به فعال قبلی، سپس ایجاد جدید |
| هم‌زمانی | `lockForUpdate` + K-6 + نگاشت استثنا |
| نمونهٔ معتبر | `A: started 2026-01-01 · ended 2026-06-30` + `B: started 2026-07-01 · ended NULL` |
| نمونهٔ نامعتبر | دو ردیف `ended_at IS NULL` با `membership_type='supervisor'` روی یک Project |
| صفر ناظر | **مجاز و پذیرفته‌شده** (OD-8/B-2) — پروژه تا تخصیص کنترل‌شده «بی‌ناظر» می‌ماند |

## 8) Historical Semantics

| مفهوم | تعریف |
|---|---|
| **active assignment** | `ended_at IS NULL` (و در V11-01: `membership_type='supervisor'`) |
| **historical assignment** | `ended_at IS NOT NULL` — ردیف باقی می‌ماند |
| **replacement** | پایان دادن به فعال قبلی + ایجاد تخصیص جدید در یک تراکنش |
| **ended assignment** | همان historical؛ تنها معنایش «دیگر scope عملیاتی ندارد» است، نه «حذف شد» |

**تصمیم دربارهٔ حذف:** ردیف‌های membership **حذف نمی‌شوند**:
- `onDelete('restrict')` روی FKها (K-1..K-3) هر حذف ضمنی/آبشاری را می‌بندد.
- **صفر soft delete** (ستون `deleted_at` ساخته نمی‌شود) — قرینهٔ `ModuleStage`: «no Soft Delete … would orphan approval history»؛ soft delete رکورد تاریخی را از query پیش‌فرض پنهان می‌کند و با الزام «تخصیص قبلی باید تاریخی بماند» در تنش است.
- **صفر مسیر حذف** در V11-01 (هیچ route/متد سرویسِ delete طراحی نمی‌شود). Modeling پشتیبان (pluggable): قید مدل به سبک C-10 (`static::deleting(fn () => false)`) — پیشنهاد می‌شود، ولی اختیاری است؛ تریگر `trg_project_memberships_no_delete` (قرینهٔ `trg_spa_no_delete`/`trg_activity_logs_no_delete`) به‌عنوان **OPTIONAL** علامت خورده و اجرای آن در دروازهٔ پیاده‌سازی تعیین می‌شود.

**تمایز حیاتی (تکرار الزام Owner):**

```text
Historical visibility            ≠     Current operational authorization
────────────────────────────────────────────────────────────────────────
ردیف تاریخی در DB می‌ماند               scope عملیاتی = فقط تخصیص فعال
و از مسیرهای system-wide                (ended_at IS NULL)
(audit/reports) قابل استعلام است
```

ناظرِ پایان‌یافته در V11-01 **scope عملیاتی** ندارد؛ دسترسی تاریخی او از مسیرهای system-wide موجود (Audit طبق DEC-045 · Reports طبق F-4) تأمین می‌شود که در این طراحی **دست‌نخورده** می‌مانند.

## 10) Project Scope Architecture (منبع واحد)

**تصمیم:** یک سرویس قاعدهٔ واحد در **`app/Domain/Rules/ProjectScopeService.php`** — دقیقاً کنار `TaskScopeService` (C-13: محل استقرار قواعد scope در مخزن).

```text
User ──▶ Permission (Spatie: ۱۱ permission سیستم‌کنترل)
     ──▶ Project Scope (ProjectScopeService)
     ──▶ Resource Authorization (Policy: Permission AND Scope AND Resource relationship)
     ──▶ Business Invariants (Service Guard — دست‌نخورده)
```

طرح API (بدون پیاده‌سازی):

| متد | معنا |
|---|---|
| `isUnrestricted(User $actor): bool` | `admin` یا `management` ⇒ scope محدودکننده ندارد |
| `accessibleProjectIds(User $actor): ?Collection` | `null` = unrestricted؛ در غیر این صورت مجموعهٔ `project_id`های مجاز |
| `canAccessProject(Project $project, User $actor): bool` | بررسی یک پروژه |
| `assertCanAccessProject(Project $project, User $actor): void` | throw `ProjectScopeViolationException extends DomainException` (قرینهٔ `ContractorScopeViolationException`، C-16) |
| `applyProjectScope(Builder $query, User $actor, string $projectColumn = 'project_id'): Builder` | Query Scope برای منابعی که ستون پروژه مستقیم دارند |
| `applyProjectScopeVia(Builder $query, User $actor, string $relation): Builder` | برای منابع غیرمستقیم (`whereHas($relation, fn ($q) => whereIn project_id)`) |

قاعدهٔ تفکیک نقش (بدون اختراع قاعدهٔ جدید):

| نقش | scope پروژه‌ای V11-01 | مبنا |
|---|---|---|
| **supervisor** | فقط پروژه‌هایی که **تخصیص فعال supervisor** دارد | تأییدشده (Assigned-based) |
| **employer** | **اعمال نمی‌شود (DEFERRED)** — رفتار فعلی (بدون scope) حفظ می‌شود | OD-2 (پیاده‌سازی موکول) |
| **admin** | `isUnrestricted = true` | تأییدشده |
| **management** | `isUnrestricted = true` | تأییدشده |
| **project_manager** · **viewer** | **اعمال نمی‌شود** — رفتار فعلی حفظ می‌شود (مبنای scope برای این دو نقش تصویب نشده) | `DO NOT INVENT` ⇒ پرسش باز Q1 (بخش ۲۴) |
| **contractor** | **دست‌نخورده** — scope پیمانکاری موجود (`TaskScopeService` + فیلترهای کنترلر) حفظ می‌شود | DEC-051 · RSK-9 |
| سایر (بدون نقش) | بدون scope (رفتار فعلی) | — |

**نقطهٔ اتصال آیندهٔ Employer:** تنها جای تغییر، شاخهٔ `employer` در `accessibleProjectIds()` است. Policyها و Query Scopeها فقط با این سرویس کار می‌کنند ⇒ افزودن scope قراردادی بعداً **بدون بازنویسی Policyها** ممکن است (بخش ۱۵).

## 11) Policy Design

**وضعیت فعلی (تأیید مجدد):** صفر کلاس Policy · صفر `Gate::define` · فقط ۲ `->can()` (permission) در `ApprovalController`. ⇒ V11-01 **زیرساخت Policy** را می‌سازد.

**محل و ثبت:** کلاس‌ها در `app/Policies/` با نام‌گذاری متعارف `{Model}Policy` (auto-discovery پیش‌فرض Laravel) ⇒ **صفر تغییر در `AppServiceProvider`** و **صفر `Gate::define`** (ممنوع).

| فاز (طبق DEC-049) | Policy | Abilities (فقط نگاشت‌شده به route/use-case **موجود**) |
|---|---|---|
| **زیرساخت V11-01** | `ProjectPolicy` | `viewAny` (`modules.index` — فهرست پروژه‌ها) · `view` (`projects/{project}/modules`) · `manageStructure` (`modules.store/rebalance/update`, `wbs-phases.store`) |
| **۱ — Tasks** | `TaskPolicy` | `viewAny` (`tasks.index`) · `view` (`tasks.show`, `tasks.edit`(orphan), `audit.task`) · `create` (`tasks.create/store`) · `assign` (`tasks.assign`) · `setStage` (`tasks.stage`) · `start` (`tasks.start`) · `submit` (`tasks.submit`) · `addDependency`/`removeDependency` (`tasks.dependencies.*`) · `uploadDocument` (`documents.store`) · `requestApproval` (`approvals.store`) |
| **۲ — Approvals** | *(Policy جدید لازم نیست)* | مسیر `approvals.store` هم‌اکنون `{task}` را bind می‌کند ⇒ `TaskPolicy::requestApproval` کافی است. **Permission** موجود (`technical_approval`/`final_approval`) به‌عنوان permission-gate باقی می‌ماند و **دو-مرحله‌ای‌بودن** (چه‌کسی مجاز است) invariant سرویس می‌ماند |
| **۳ — Modules** | `ModulePolicy` · `ModuleStagePolicy` | `viewAny`/`view` (`modules.index`, `modules.show`, `modules.stages.show`) · `manage` (`modules.*`، `stages/*/progress-approvals`) |
| **۴ — Wbs** | `WbsPhasePolicy` | `viewAny`/`view` (`wbs-phases.index/show`) · `manage` (`wbs-phases.store`, checklist `add/complete/reopen`) · `decide` (`wbs-phases.decide`) |
| **ممنوع در V11-01** | abilities برای عملیات **ناموجود** (`TaskPolicy::update`/`delete` برای `tasks.update/destroy` که متد کنترلر ندارند) | C-18 — طراحی برای عملیاتی که وجود ندارد = اختراع سطح حمله؛ **صفر ability** |
| **صفر Policy (عمدی)** | Report · Audit · Settings · User · Dashboard · Document (مستقل) | بخش ۱۶ (`INTENTIONALLY SYSTEM-WIDE` / admin-only / بدون Policy) |

**الگوی داخلی هر Policy (طرح):** `view(User $actor, Model $resource): bool` ⇒ `Permission (در صورت وجود) && ProjectScopeService::canAccessProject($resource->project...) && (قاعدهٔ رابطهٔ منبع)`. `viewAny` ⇒ فقط permission + scope-type (چون رکوردی وجود ندارد؛ فیلتر واقعی با Query Scope انجام می‌شود).

**سمانتیک رد (403):** `authorize()` پیش‌فرض Laravel `AuthorizationException` → **403**، هم‌راستا با `abort(403, ...)` موجود در کنترلرها (C-19). 404 (پنهان‌سازی وجود منبع) به‌عنوان جایگزین بررسی شد و رد می‌شود تا رفتار reposiory یکنواخت بماند و خطاها قابل‌دیباگ باشند. (بازگشت به 404 = تغییر یک خط در `bootstrap/app.php` — بدون اثر روی Policyها.)

## 14) Service Guard Design

**قاعدهٔ قفل‌شده:** Policy = **Authorization**؛ Service = **Business Invariants**. Policy **هرگز** جای invariant را نمی‌گیرد و نمی‌تواند از آن عبور کند.

| سرویس | Invariantهای موجود (دست‌نخورده) |
|---|---|
| `TaskService` | `authorizeStageAssignment` (فقط supervisor — DEC-042) · `assertStageChangeAllowed` (قفل پس از `approved`/`cancelled` — DEC-043) · cross-project stage rejection · state machine (`startProgress`, `submitForReview`) |
| `ApprovalService` | دو-مرحله‌ای بودن technical/final · فقط Employer برای `final_approval` · ترتیب sequence |
| `StageProgressApprovalService` | mode-based authorization (`progress_approval_mode`) · سقف تجمعی (ceiling) · immutability · زنجیرهٔ supersede · وزن قفل‌شده |
| `ModuleService` / `ModuleStageService` | `SUM(weight) = 100` با parent lock · lock وزن پس از اولین approval (OQ-05=3A) |
| `WbsPhaseService` | انتقال‌های وضعیت فاز · completion از Checklist + تأیید ناظر (نه از completion تسک) |
| `SlaService` · `WeightChangeRequestService` | بدون تغییر |
| `TaskScopeService` (contractor) | **حفظ کامل** — scope پیمانکاری در V11-01 تغییر نمی‌کند |

**الگوی اجرا در مسیر درخواست (طرح):**

```text
Controller/FormRequest
   │  authorize() → Policy            ← Permission AND Project Scope AND relationship
   ▼
Service Guard (domain)                ← invariants؛ مستقل از Policy
   ▼
DB (constraints/triggers)             ← آخرین سد (K-4..K-6، تریگرهای V1.8)
```

آزمون کلیدی (بخش ۲۲): «Policy اجازه می‌دهد اما invariant نقض است» ⇒ باید **استثنای دامنه** بدهد، نه ALLOW.

## 16) Admin / Management

**تعریف «Unrestricted» (قفل‌شده):** فقط و فقط **عدم محدودیت Project Scope**.

```text
Unrestricted  ⇒  Project Scope = همهٔ پروژه‌ها            ✅
Unrestricted  ⇏  bypass Permission                        ❌
Unrestricted  ⇏  bypass Business Invariants               ❌
Unrestricted  ⇏  bypass مرزهای مالی                       ❌
Unrestricted  ⇏  bypass Audit                             ❌
Unrestricted  ⇏  bypass امنیت                             ❌
```

**الگوی پیاده‌سازی (طرح):** `ProjectScopeService::isUnrestricted()` مقدار «همهٔ پروژه‌ها» را برمی‌گرداند و `applyProjectScope()` برای این دو نقش **هیچ شرطی اضافه نمی‌کند**. **`Gate::before` ساخته نمی‌شود** — چون یک bypass سراسری، Permissionها و invariants را هم دور می‌زند (نقض DEC-050).

**پیامد مهم:** Management فقط permissionهای `view reports`/`export reports` را دارد ⇒ «unrestricted» او را قادر به هیچ اقدام نوشتنی نمی‌کند (permission همچنان محدودکننده است). Admin همهٔ ۱۱ permission را دارد ⇒ محدودیت scope ندارد، ولی همچنان تابع invariants است.

## 18) Permission Integration

مدل قفل‌شده: `User → Role` · `Role → Permission` · `User → Direct Permission` · Effective = Role + Direct · **Grant-only · صفر Deny** · کاتالوگ سیستم‌کنترل · **صفر Dynamic Permission → Route mapping**.

### 18.1 چهار حالت الزامی (طرح نمونهٔ مفهومی — پیاده‌سازی نمی‌شود)

| # | Permission | Project Scope | Invariant | نتیجه | چرا |
|---|---|:-:|:-:|:-:|---|
| 1 | ❌ | ✅ | — | **DENY** | انتساب به پروژه مجوزِ اقدام نیست (`Scope ≠ Permission`) |
| 2 | ✅ | ❌ | — | **DENY** | permission برای منبع project-scoped کافی نیست (`Permission ≠ Scope`) |
| 3 | ✅ | ✅ | ✅ | **ALLOW** | هر سه شرط |
| 4 | ✅ | ✅ | ❌ | **DENY** | Service Guard مستقل و برتر (مثلاً stage پس از final approval · ceiling) |

### 18.2 نمونهٔ عینی

```text
User U (نقش supervisor):
  Permission: technical_approval ✅ · tasks assign ندارد ❌
  Membership: Project X → supervisor ACTIVE ✅ · Project Y → ندارد ❌

Task T_X ∈ X ⇒ Policy: permission ✅ AND scope ✅        ⇒ ALLOW (سپس invariant سرویس)
Task T_Y ∈ Y ⇒ Policy: permission ✅ AND scope ❌        ⇒ DENY 403
Task T_X (assign) ⇒ permission ❌                       ⇒ DENY 403
```

### 18.3 مرزها

| قاعده | طرح |
|---|---|
| `membership_type` **هرگز** جای permission را نمی‌گیرد | فقط برچسب scope؛ صفر نگاشت به route/permission |
| صفر Deny | هیچ permission منفی/Deny ساخته نمی‌شود |
| صفر permission جدید | کاتالوگ ۱۱ موردی دست‌نخورده می‌ماند (افزودن permission = DEC-050 territory) |
| Scope ≠ Permission | هر دو لازم‌اند (حالت‌های ۱ و ۲) |
| Invariant > Policy | حالت ۴ |
