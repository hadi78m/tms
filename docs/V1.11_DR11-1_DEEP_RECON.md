**Evidence:** Part A/B/C/H — هیچ رابطهٔ Project↔User موجود نیست؛ تنها مورد ممکن Migration است.

**گزینه‌ها:** H-A (`project_user`) · H-B (`project_supervisors`) · H-C (`project_memberships` + role) · H-D (ستون روی `projects`) · H-E (نامعتبر).

**Evidence:** Part F (هیچ scope پروژه‌ای در هیچ لایه وجود ندارد؛ صفر Policy/Gate؛ الگوی غالب `role:` middleware + گارد دامنه).

**Tradeoffs:** G-A ساده ولی نشت لیست · G-B دفاعی، نیازمند scope واحد مشترک · G-C قوی‌ترین، پیچیده‌ترین · G-D منطبق با دامنهٔ فعلی، ریسک فراموشی فراخوانی · G-E سبک، ضعیف.

# PART J — DR-11-1 FINAL OWNER DECISION (ثبت‌شده 2026-09-28)

> این بخش **تصمیم مالک** است (نه یافتهٔ reconnaissance و نه فرض مهندسی). بخش‌های A–I بدون تغییر باقی می‌مانند. تصمیم به‌عنوان تکمیل **DEC-048** ثبت می‌شود (زیرجزء ② و ③ بخشی از همان DR-11-1 هستند؛ **شمارهٔ DEC جدید ساخته نمی‌شود**).

## B) تصمیم مالک — ② Membership / Assignment Structure

**تصمیم:** **H-C — Project Membership / Assignment Structure**

| بند | تصمیم مالک |
|---|---|
| ساختار | رابطهٔ Project ↔ User از طریق یک **ساختار عضویت/تخصیص اختصاصی پروژه‌ای** نمایندگی می‌شود (جدول membership/assignment پروژه‌ای). |
| تاریخ‌مندی | ساختار **باید** از تخصیص تاریخی پشتیبانی کند (دورهٔ start/end). |

| گزارش/audit | تخصیص‌های تاریخی برای مقاصد historical/audit/reporting در جایی که مصداق دارد در دسترس می‌مانند. |

### B.1 قاعدهٔ cardinality ناظر (تصمیم مالک)

- برای هر Project، **حداکثر یک Supervisor در هر زمان می‌تواند ACTIVE باشد**.
- تخصیص‌های تاریخی ناظر **حفظ می‌شوند**.
- تخصیص جدید می‌تواند تخصیص فعال قبلی را **جایگزین/پایان** دهد.
- سیستم **نباید** صرفاً به‌دلیل پایان‌یافتن، تخصیص قبلی را حذف کند.

نمونهٔ مرجع مالک:

```text
Project X

Supervisor A:  01/01/2026 → 30/06/2026   (historical)
Supervisor B:  01/07/2026 → ACTIVE       (current)

⇒ در هر زمان فقط یک ناظر فعال؛ A تاریخی می‌ماند.
```

**Not-invented:** پیاده‌سازی قاعدهٔ یکتا، ایندکس یکتای دقیق و معنای تاریخ/timezone متعلق به دروازهٔ بعدی است.

## B) تصمیم مالک — ③ Enforcement Layer

**تصمیم:** **G-C — Middleware + Policy + Service Guard** با **Query Scope** به‌عنوان مکانیزم پشتیبان برای project-scoped retrieval.

### تفکیک مسئولیت‌ها (الزام ثبت‌شده)

| لایه | مسئولیت | محدودیت |
|---|---|---|
| **Middleware** | کنترل دسترسی درشت‌دانه (coarse-grained): «آیا کاربر مجاز به ورود به این ناحیهٔ عملکردی است؟» مکانیزم‌های role-based موجود معتبر می‌مانند. | **ممنوع:** قرار دادن Business Invariant در middleware. |
| **Policy** | **Resource Authorization** — آیا کاربر مجاز به عملیات روی این منبع خاص است؟ Project Scope باید در resource authorization مشارکت کند: `Permission + Project Scope + Resource relationship`. | **ممنوع:** کافی دانستن Permission به‌تنهایی برای منبع project-scoped. |
| **Query Scope** | مکانیزم **پشتیبان** مجوزدهی/جداسازی داده: `User → Accessible Projects → Project Resources` — جلوگیری از retrieval منابع پروژه‌ای غیرمجاز. | **ممنوع:** تفسیر Query Scope به‌عنوان **جایگزین** Policy. |
| **Service Guard** | **Business Invariants** — قواعد دامنهٔ موجود (final approval restrictions · stage locking · state transitions · سایر قواعد دامنهٔ موجود). | **ممنوع:** تلقی مجوز Policy به‌عنوان اجازهٔ عبور از Business Invariants. |

## C) قیدهای پیاده‌سازی (Implementation Constraints)

1. **جداسازی مفاهیم (غیرقابل ادغام):** `Permission = چه کاری مجاز است` · `Project Scope = روی کدام پروژه/منبع` · `Policy = Resource Authorization` · `Query Scope = جلوگیری از retrieval غیرمجاز` · `Service Guard = Business Invariants`.
2. **Permission نباید** به‌طور خودکار دسترسی همهٔ پروژه‌ها بدهد؛ نباید Project Scope، Business Invariants یا مرزهای مالی را override کند.
3. **Project Scope نباید** جایگزین پنهان سیستم Permission شود.
4. **سازگاری با DEC-050:** مدل Dynamic Role + Permission Assignment دست‌نخورده می‌ماند (`User→Role` · `Role→Permission` · `User→Direct Permission` · effective = Role + Direct · **Grant-only · صفر Deny** · کاتالوگ سیستم‌کنترل · **صفر Dynamic Permission→Route mapping**). ⇒ **Permission System ≠ Project Membership/Scope** و ادغام نمی‌شوند.
5. **Hybrid scope (DEC-048) دست‌نخورده:** `Employer = Contract-based` · `Supervisor = Assigned-based` · `Admin/Management = Unrestricted`. معنای فنی «unrestricted» در این فاز **بازتفسیر/گسترش نمی‌شود** — متعلق به دروازهٔ implementation/design بعدی است. هیچ رفتار bypass جدیدی معرفی نمی‌شود.
6. **اولویت مهاجرت Policy (DEC-049) حفظ می‌شود:** `Tasks → Approvals → Modules → Wbs`؛ هر مرحله مستقل با implementation · tests · authorization verification · regression verification · acceptance.
7. **گاردریل‌های Contractor (DEC-051) حفظ می‌شوند:** OQ-32 = **DEFERRED/BLOCKED** · صفر بُعد contractor · صفر `contractor_id` روی `tasks`/stages/approvals/`performance_records` · پیمانکار موجودیت تاریخی پایدار · پایان قرارداد نباید دادهٔ تاریخی را حذف/جدا/غیرقابل‌دسترسی کند.
8. **Audit (DEC-045) و Masking (DEC-053) دست‌نخورده:** read-only · supervisor+employer · masking · DEC-053 فقط assertion تست.
9. **Legacy (DEC-052) دست‌نخورده:** فقط حذف `wbs_phases.weight`؛ `tasks.weight` و DEC-036/R1-F1 باز نمی‌شوند.
10. **Service guardهای موجود حفظ می‌شوند و دور زده نمی‌شوند.**
11. **Role middlewareهای موجود معتبر می‌مانند** — G-C آن‌ها را حذف/تضعیف نمی‌کند؛ فقط Policy + Query Scope + Service Guard به‌عنوان لایهٔ project-scope افزوده می‌شوند.
12. در این فاز **صفر** کد/Policy/Middleware/Query Scope/Migration/Schema/Route/Test/UI.
