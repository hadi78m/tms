## T-3

### Current Model

رد در سیستم از طریق `task_approval_recorded` (با گذار status به `needs_rework`) +
Audit Trail کامل ثبت می‌شود. تراکنشی، بدون bypass، بدون اطلاعات گم‌شده.

### Option A — Keep Current Model

| بُعد | ارزیابی فنی |
|---|---|
| Queryability | رد قابل query است ولی شرطی: خواندن `new_values.status` از JSONB |
| Auditability | کامل — هم‌اکنون existing |
| Event semantics | رد مفهوم درجه‌یک نیست؛ از ترکیب approval+status مشتق می‌شود |
| Reporting | گزارش «همهٔ ردها» به تفسیر JSONB نیاز دارد |
| Event consumers | مصرف‌کنندهٔ خارجی باید بدنهٔ JSON را تفسیر کند |
| Backward compatibility | حفظ وضع موجود = صفر ریسک |
| Implementation complexity | صفر |

### Option B — Add `task_rejected`

اگر Owner انتخاب کند، تغییرات احتمالی این‌ها خواهد بود (فقط فهرست — **اجرا نشده**):

```text
Event definition ....... رشتهٔ رویداد جدید در activity_logs (ستون event آزاد است —
                         صفر Schema change · صفر Migration · صفر Enum جدید)
Dispatch points ........ پس از task_approval_recorded در
                         ApprovalService::recordTechnicalApproval() و
                         recordFinalApproval()، درون همان transaction، فقط وقتی
                         status = needs_rework
                         (needsRework عمومی و مسیر وزن تکرار نمی‌کنند — شمارش دوگانه ممنوع)
Tests ................. رد فنی → رویداد · رد نهایی → رویداد · تأیید → بدون رویداد
Audit/event consistency . additive — هیچ رویداد موجودی تغییر نمی‌کند
Reporting/query ........ گزارش «همهٔ ردها» بدون تفسیر JSONB — ارزش گزارش‌پذیری
```

## T-5

### Current Model

هیچ مسیر حذف Project وجود ندارد. حذف سخت (hard delete) در DB با RESTRICT مسدود است.
SoftDeletes روی مدل فعال است اما هرگز فراخوانی نمی‌شود.

### Option A — No Project Delete Capability

| بُعد | ارزیابی فنی |
|---|---|
| قابلیت | حذف/بایگانی Project از طریق application ارائه نمی‌شود؛ پاک‌سازی خارج از سیستم |
| Data integrity | حداکثر — هیچ مسیر حذف، هیچ invariant جدید |
| Restore | N/A |
| تغییرات لازم | صفر (وضعیت فعلی همین است) |
| محدودیت | اگر در آینده نیاز واقعی به حذف/بایگانی باشد، باید همین دروازه دوباره باز شود |

### Option B — Soft Delete Only (شرط‌دار به تعریف مالک)

اگر Owner انتخاب کند، implementation بعدی نیازمند تعریف صریح این‌ها خواهد بود
(**بدون تعریف در این گزارش**):

```text
شروط حذف نرم ....... کدام شرایط (مثلاً وضعیت ماژول‌ها) — قاعده را مالک تعیین می‌کند
سرویس/route ........ نقطهٔ ورود حذف نرم (فعلاً صفر مسیر موجود)
visibility rules ... فیلتر deleted_at در queryهای گزارش (بازرسی لازم)
restore behavior ... چه کسی، چه زمانی
تست‌ها ............. حذف/شرط/restore/RESTRICT hard-delete
Migration .......... صفر (ستون deleted_at موجود است)
```

### Option C — Archive

به‌جای Delete، Project به وضعیت Archive منتقل شود. اگر انتخاب شود، implementation
بعدی نیازمند تعریف دقیق:

```text
archive state ....... مکانیزم (deleted_at یا فیلد وضعیت جدید — تصمیم مالک)
visibility rules .... کجاها پنهان، کجاها فقط-خواندنی
access rules ........ نقش‌های مجاز به بایگانی/خروج از بایگانی
reporting behavior  رفتار گزارش‌ها نسبت به پروژهٔ بایگانی‌شده
restore behavior .... فرایند بازگردانی
Migration ........... اگر فیلد وضعیت جدید لازم شود → Migration (فعلاً مجاز نیست)
```
