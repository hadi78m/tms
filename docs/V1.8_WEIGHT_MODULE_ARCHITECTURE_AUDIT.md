## 0. خلاصه اجرایی

این سند، تصمیمات قطعی مالک پروژه در فاز V1.8 را روی Repository موجود تطبیق می‌دهد. یافته‌های اصلی:

1. **مدل مورد نظر مالک پروژه دو موجودیت مفهومی جداگانه دارد که امروز هر دو در یک جدول ادغام شده‌اند:** «WBS Phase» (محدوده، تاریخ، خروجی، Checklist، تأیید نهایی ناظر) و «Module Stage» (سهم وزنی استاندارد). جدول `wbs_phases` امروز فقط دومی را به‌صورت ناقص نمایندگی می‌کند و اولی را ندارد.
2. **موجودیت Module / Deliverable در Repository وجود ندارد.** سلسله‌مراتب امروز `Contract → Project → WbsPhase → Task` است.
3. **`tasks.weight` در تناقض مستقیم با تصمیم قطعی است** و در همان حال NOT NULL، الزامی در UI، پرخواننده در ۴ نما، و تغذیه‌کنندهٔ گزارشی با برچسب «آماده پرداخت» است.
4. **`wbs_phases.weight` دادهٔ مرده است** (صفر مصرف‌کننده، صفر تست) و معنایش با مدل جدید جابه‌جا می‌شود.
5. **`expected_output` یک فیلد TEXT واحد است، نه Checklist.** مدل تأیید ناظر بر مبنای Checklist (§۵/§۶) امروز هیچ بازنمایی ندارد.
6. **کل Audit Trail در محیط اجرا مرده است** (`AuditServiceInterface` به `NullAuditService` بایند شده). الزام §۱۳ (تاریخچه تغییرات درصد) بدون رفع این، قابل تحقق نیست.
7. **تناقض مستنداتی:** `docs/01-project-overview.md` بند ۶ می‌گوید «وزن Task یا مرحله باید از ابتدا مشخص شود» — این با تصمیم قطعی جدید (Task وزن ندارد) مستقیماً متناقض است.

### 3.3 نکته ساختاری حیاتی — تفکیک دو مفهوم

مدل بخش §۵ پرامپت صریحاً می‌گوید:

> «WBS Phase صرفاً یک درصد وزنی از Project نیست.»

و مثال §۵:

```text
Phase 1
عنوان: تحلیل، طراحی، معماری
Expected Outputs: SRS, ERD, DFD, UI/UX Prototype, Technical Stack, Schedule, Documentation, Git Delivery
```

این مثال **یک** WBS Phase را نشان می‌دهد که **دو** Stage (`Analysis` + `Design`) را پوشش می‌دهد. بنابراین:

> **WBS Phase و Module Stage دو موجودیت متفاوت با دو نقش متفاوت‌اند و نباید در یک جدول ادغام شوند.**

| بُعد | WBS Phase | Module Stage |
|---|---|---|
| ماهیت | محدوده و برنامهٔ اجرایی | سهم استاندارد وزنی |
| مالک وزن | ❌ | ✅ |
| تاریخ شروع/پایان | ✅ | ❌ (معمولاً) |
| مدت تخمینی | ✅ | ❌ |
| Expected Outputs / Checklist | ✅ | ❌ |
| تأیید نهایی | ناظر (Binary: Completed / Not Completed) | Employer/Supervisor (کمی: درصد) |
| تعداد در Project | متغیر | ۹ × تعداد Module |
| استاندارد بودن | آزاد | ثابت (کاتالوگ) |
| مرجع تصمیم | §۵، §۶ | §۴، §۷، §۹ |

**این تفکیک در Repository امروز وجود ندارد.** جدول `wbs_phases` هم‌زمان تلاش می‌کند هر دو باشد: `weight` (نقش Stage) + `start_date`/`end_date`/`expected_output`/`planned_duration` (نقش Phase). نتیجه: نه Stage واقعی است، نه Phase کامل — و `weight` آن صفر مصرف‌کننده دارد.

### 3.4 تحلیل Constraint مجموع وزن Moduleها (§۳ پرامپت)

مالک پروژه سه احتمال را مطرح کرده و صریحاً گفته **تحلیل بده و Constraint نساز**. تحلیل:

| گزینه | تحلیل | پیامد |
|---|---|---|
| **(الف) دقیقاً 100** | مثال §۳ (40+35+25=100) به این گزینه اشاره دارد. چون Support (15%) **درون** هر Module است، وزن Module سهم توسعهٔ خالص نیست، بلکه سهم کل تحویل شامل پشتیبانی است | سخت‌گیرانه؛ اگر Project ماژول غیرتوسعه‌ای داشته باشد (مثلاً سخت‌افزار، آموزش عمومی) قابل اعمال نیست |
| **(ب) فقط Moduleهای توسعه‌ای کنترل شود** | با `module.kind = 'development'` قابل اعمال است. Moduleهای غیرتوسعه‌ای از قید خارج می‌شوند | انعطاف‌پذیرتر؛ اما نیازمند یک ستون `kind` که هنوز مصوب نشده |
| **(ج) وابسته به Contract / Project** | `projects` امروز ۱:۱ با قرارداد است، پس «سطح Project» و «سطح قرارداد» عملاً یکی‌اند. تفکیک آن‌ها امروز معنای اضافه دارد | افزودن پیچیدگی بدون فایدهٔ فعلی |

**نتیجه تحلیل (بدون تصمیم‌گیری):**

- جدول `deliverables` هیچ ستون کنترلی امروز ندارد، پس **هیچ Constraint موجودی نقض نمی‌شود** — این یک تصمیم تازه است، نه اصلاح.
- در Repository موجود، **دقیقاً یک نمونهٔ مشابه** برای الگوگیری وجود دارد: قاعدهٔ «مجموع وزن فازهای یک Project = 100» که در `docs/database_physical_design_v1.5.md:113` و `TMS_PROJECT_TRACKER.md §6` به‌عنوان «Application Layer Rule» ثبت شده و **هرگز پیاده‌سازی نشده است**.
- **هشدار:** تکرار همان الگو (ثبت قاعده در لایه Application بدون پیاده‌سازی) منجر به همان نتیجه می‌شود. هر گزینه‌ای انتخاب شود باید در Service با تست واقعی پیاده شود، نه در مستندات.
- تفاوت مهم با گزینهٔ فعلی: مجموع وزن Moduleها **قابل محاسبه در لحظهٔ درج** است (برخلاف تأییدهای تجمعی) و می‌تواند به‌صورت Row Lock در `ModuleService` کنترل شود.

**تصمیم لازم:** `OQ-01` در بخش ۱۷.

## 4. Module / Deliverable Model

### 4.1 موجودیت پیشنهادی

طبق BD-02 و BD-03، Module موجودیتی **جدید** است که زیر Project قرار می‌گیرد.

```text
modules   (نام جایگزین قابل بحث: deliverables)
─────────────────────────────────────────────────────────
id                BIGINT PK IDENTITY
project_id        BIGINT NOT NULL FK → projects  RESTRICT
name              VARCHAR(255) NOT NULL
code              VARCHAR(100) NULLABLE
description       TEXT NULLABLE
weight            NUMERIC(5,2) NOT NULL        ← سهم این Module از Project
kind              VARCHAR(50) NOT NULL         ← development | support_only | other   (نیازمند تصمیم OQ-01)
status            VARCHAR(50) NOT NULL
start_date        DATE NULLABLE
end_date          DATE NULLABLE
sort_order        INTEGER NOT NULL DEFAULT 0
created_at/updated_at  TIMESTAMPTZ
deleted_at        TIMESTAMPTZ NULLABLE
UNIQUE (project_id, code)
CHECK (weight > 0 AND weight <= 100)
CHECK (end_date IS NULL OR start_date IS NULL OR end_date >= start_date)
INDEX (project_id)
```

**نکات طراحی:**

1. `UNIQUE (project_id, code)` — جلوگیری از تکرار شناسهٔ ماژول. اگر `code` NULL باشد، PostgreSQL مقادیر NULL را متمایز می‌داند (رفتار `UNIQUE` استاندارد)، پس ماژول‌های بدون code محدود نمی‌شوند. اگر این رفتار نامطلوب است → `OQ-02`.
2. `kind` **فقط پیشنهاد** است و به تصمیم OQ-01 وابسته. اگر گزینهٔ (ب) انتخاب نشود، این ستون لازم نیست.
3. `weight` **بدون هیچ Constraint مجموعی** در Database — مطابق دستور صریح §۳ که Constraint جدید ممنوع است.
4. الگوی Constraintها دقیقاً مطابق سبک موجود Repository: `DB::statement('ALTER TABLE ... ADD CONSTRAINT chk_...')` برای CHECKها، همان‌طور که در `create_wbs_phases_table.php:31` و `create_projects_table.php` انجام شده.

### 4.2 رابطه با موجودیت‌های موجود

| رابطه | تغییر | توضیح |
|---|---|---|
| `modules.project_id → projects` | 🆕 جدید | Project امروز کانتینر است و این رابطه با معنای فعلی آن سازگار است |
| `wbs_phases.deliverable_id → modules` | ❓ **نیازمند تصمیم** | آیا WBS Phase به Module وصل می‌شود؟ بخش §۵/§۶ این را الزام نکرده. `OQ-03` |
| `tasks.module_stage_id` | 🆕 پیشنهادی | برای اتصال Task اجرایی به Stage |
| `tasks.wbs_phase_id` | ✅ **KEEP** | امروز NULLABLE و RESTRICT است — دقیقاً همان چیزی که مدل جدید لازم دارد |

### 4.3 وضعیت فعلی که مانع می‌شود

`projects.contract_id` **UNIQUE** است (۱:۱ با قرارداد). مدل جدید «چند Module در یک Project» می‌خواهد، نه «چند Project در یک قرارداد». پس **این UNIQUE نیازی به تغییر ندارد** — Moduleها فرزندان Project هستند، نه هم‌تراز آن. این یعنی بخش عمده‌ای از ریسک R-01 فاز ممیزی قبلی **منتفی** شد.

### 5.2 جایگاه ذخیره

**پیشنهاد:** یک ردیف فیزیکی در جدول `module_stages` به‌ازای هر Stage هر Module.

```text
module_stages
─────────────────────────────────────────────────────────
id                BIGINT PK IDENTITY
module_id         BIGINT NOT NULL FK → modules  RESTRICT
stage_code        VARCHAR(50) NOT NULL       ← کلید کاتالوگ ۹گانه
name              VARCHAR(255) NOT NULL      ← قابل بازنویسی توسط کاربر
weight            NUMERIC(5,2) NOT NULL      ← سهم از ۱۰۰ ماژول
sort_order        INTEGER NOT NULL DEFAULT 0
created_at/updated_at  TIMESTAMPTZ
UNIQUE (module_id, stage_code)
CHECK (weight > 0 AND weight <= 100)
INDEX (module_id)
```

**چرا ردیف فیزیکی و نه Enum سخت‌کد:**

- درصدها باید در UI نمایش داده شوند و **تأیید تجمعی** روی آن‌ها ثبت شود → نیاز به FK از `stage_progress_approvals`.
- اگر روزی وزن‌ها تغییر کنند، رکوردهای تأیید تاریخی باید همچنان به مقدار معتبر اشاره کنند.
- الگوی موجود Repository برای وضعیت‌ها **Enum در `app/Domain/Enums`** است (۸ Enum موجود). `StageCode` باید به‌عنوان Enum ساخته شود و مقدار آن در ستون `stage_code` بنشیند — ترکیب Enum + ردیف فیزیکی، هم‌خوان با سبک موجود.

### 5.3 محاسبهٔ سهم Stage نسبت به Project (§۴ پرامپت)

پرامپت مثال زده: `Module A = 40%` از Project، پس `Analysis` این Module از نظر محاسباتی «۴۰٪ × ۱۵٪» است.

**تحلیل ریاضی (بدون پیاده‌سازی):**

```text
stage_share_of_project = module.weight × stage.weight / 100
                       = 40 × 15 / 100 = 6%
```

نتیجه: سهم Project از یک Stage می‌تواند اعشاری باشد (۶٪، ۲٪، ۱۴٪، …). این یعنی:

- `NUMERIC(5,2)` برای درصد Stage **کافی است** (حداکثر ۱۰۰.۰۰).
- در صورت نیاز به تفکیک اعشاری بیشتر، `NUMERIC(8,2)` موجود در `performance_records.total_weight_completed` الگوی موجود است.
- **اما** مطابق BD-22 و دستور §۴، **هیچ فرمول Progress در این فاز پیاده‌سازی نمی‌شود.** این محاسبه فقط برای اثبات کفایت نوع داده گزارش می‌شود.

### 8.1 الزام (BD-18، BD-19، BD-20)

### 8.2 نتیجه تحلیل — Support در کجا ذخیره می‌شود؟

**Support یک ردیف `module_stages` با `stage_code = 'support'` است**، نه یک `wbs_phase` و نه یک جدول مستقل.

دلایل:

1. **درصد آن (۱۵٪) از همان جنس ۱۰۰٪ ماژول است** — پس باید در همان Ledger باشد، وگرنه دو Aggregate موازی برای یک مفهوم واحد ساخته می‌شود.
2. **تأیید درصدی آن عیناً همان مکانیزم `stage_progress_approvals` را می‌خواهد** — هیچ تفاوتی در جریان تأیید ندارد.
3. **جدول مستقل، پیچیدگی بدون فایده ایجاد می‌کند:** یک `support_allocations` جدا یعنی دو مسیر برای پاسخ به سؤال «چقدر از این ماژول تأیید شده؟» و دو نقطهٔ شکست.
4. **منع §۱۰ بر «WBS Phase بودن» است، نه بر «Stage بودن».** Support نباید در `wbs_phases` بنشیند — و نمی‌نشیند.

**این تصمیم، پیشنهاد فاز ممیزی قبلی را اصلاح می‌کند:** در ممیزی V1.8 مرحلهٔ اول، گزینهٔ «Support به‌عنوان `wbs_phase` با `kind='support'`» پیشنهاد شده بود. با §۱۰ این گزینه **باطل** است. مدل صحیح: Support یک Stage درون Module است.

### 9.3 تحلیل `task_type` (§۱۲ پرامپت)

**سؤال مالک پروژه:** آیا `task_type` واقعاً لازم است، یا می‌توان رابطهٔ Task با Module/Stage را به‌عنوان منبع تشخیص استفاده کرد؟

**تحلیل — سه گزینه:**

| گزینه | مکانیزم تشخیص «تسک پشتیبانی» | مزیت | عیب |
|---|---|---|---|
| **(الف) استنتاج از رابطهٔ Stage** | `task.module_stage_id → module_stage.stage_code = 'support'` | ✅ صفر ستون جدید<br>✅ تک‌منبع حقیقت (Single Source of Truth)<br>✅ تغییر Stage تسک به‌طور خودکار نوع را عوض می‌کند | ❌ اگر تسک به هیچ Stage وصل نباشد، نوعش نامعلوم است |
| **(ب) ستون `task_type`** | مقدار صریح روی تسک | ✅ همیشه تعریف‌شده<br>✅ کوئری ساده‌تر | ❌ خطر واگرایی با Stage (تسک `support` که به Stage `coding` وصل است)<br>❌ ستون اضافه بر تصمیم BD-01 |
| **(ج) ترکیبی** | رابطهٔ Stage اولویت دارد، `task_type` فقط Fallback | ✅ پوشش هر دو حالت | ❌ دو منبع حقیقت = پیچیدگی تشخیص |

**پیشنهاد معماری (بدون تغییر Schema — مطابق دستور صریح §۱۲):**

> **گزینهٔ (الف) توصیه می‌شود** — استنتاج از رابطهٔ Stage، **بدون افزودن `task_type`**.
>
> شرط لازم: تسک‌های پشتیبانی **باید** به Stage پشتیبانی وصل شوند. امروز `tasks.wbs_phase_id` NULLABLE است و هیچ الزامی وجود ندارد — یعنی تسک‌های فعلی می‌توانند بدون هیچ اتصالی باشند. اگر مالک پروژه تأیید کند که «تسک پشتیبانی همیشه به Stage پشتیبانی وصل می‌شود»، گزینهٔ (الف) کافی است.
>
> **اگر مالک پروژه بگوید تسک پشتیبانی می‌تواند بدون هیچ اتصالی وجود داشته باشد → گزینهٔ (ب) لازم می‌شود.** این یک تصمیم کسب‌وکاری است، نه فنی → `OQ-04`.

**توجه:** در ممیزی مرحلهٔ اول این پروژه، افزودن `task_type` صریحاً در فهرست ممنوعیت‌ها بود. این تحلیل آن ممنوعیت را نقض نمی‌کند — فقط گزارش تحلیلی است و هیچ Schema تغییر نکرده.

### 10.2 حالت `supervisor_only` — الزام صریح

پرامپت §۹ صریحاً می‌گوید:

> «اگر ناظر مستقیماً درصد را تعیین کند، نباید محدود شود.»

این یعنی مدل **نباید** الزام کند که حتماً Employer مقدار را وارد کند. پیاده‌سازی: حالت `supervisor_only` در `progress_approval_mode` که در آن ناظر در یک عملیات اتمیک، هم `proposed_amount` را تعیین و هم `approved_amount` را نهایی می‌کند.

**توصیه فنی:** حتی در این حالت، رکورد با `status = 'pending'` درج و سپس گذار داده شود (نه درج مستقیم با `approved`)، تا:
- تاریخچهٔ Audit یکنواخت بماند،
- الگوی موجود `WeightChangeRequestService::approveRequest` (که `pending` را lock و سپس گذار می‌دهد) تکرار شود،
- و گزارش‌گیری «تأییدهای انجام‌شده» یک مسیر واحد داشته باشد.

### 10.3 وضعیت فعلی تشخیص Supervisor در کد

```php
// ApprovalService::recordTechnicalApproval — خط ۳۰
if ($actor->contractor_id !== null) {
    throw new InvalidApprovalException('Contractor cannot perform Technical Approval.');
}
```

**مشاهده:** تشخیص «ناظر بودن» امروز بر اساس **کلید داده** (`users.contractor_id`) انجام می‌شود، نه بر اساس **Role/Permission**. مجوز واقعی در لایه Controller با `$actor->can('technical_approval')` بررسی می‌شود (خط ۳۱ `ApprovalController`).

**برای V1.8:** همین الگو قابل تکرار است، اما توصیه می‌شود برای `stage_progress_approvals` از **Permission** استفاده شود (`manage stage progress` / `final_approve stage progress`) تا با تصمیم «داشبوردها بر اساس Role + Permission + Settings» هم‌خوان باشد. این یک پیشنهاد است، نه تغییر.

### 18.1 طبقه‌بندی بر اساس ریسک

```text
🟢 بی‌ریسک (Additive — بدون تأثیر روی موجود):

   ALTER wbs_phases DROP COLUMN weight          ← فقط پس از تأیید و انتقال داده

🟠 متوسط (تأثیر روی تست و UI):
   ALTER tasks ALTER COLUMN weight DROP NOT NULL

🔴 پرریسک (فاز بعد، نیازمند تأیید صریح):
   ALTER tasks DROP COLUMN weight
   DROP TABLE weight_change_requests
```

گام ۵ — در فاز بعد، پس از اثبات نبود خواننده:

## 20. Final Recommendation

### 20.1 پاسخ به پرسش اصلی مالکیت Weight (§۸ پرامپت مرحلهٔ قبل)

> **Weight باید در دو سطح ذخیره شود: `modules.weight` (سهم ماژول از Project) و `module_stages.weight` (سهم مرحله از ماژول). Task هیچ وزن مؤثری ندارد.**

این پاسخ از سه جهت با Repository تأیید می‌شود:

1. **الزام §۷ (۵+۷+۳=۱۵) ذاتاً درون‌فازی است** → نیازمند یک سطح زیر ماژول.
2. **الزام §۳ (مجموع ماژول‌ها) ذاتاً بالای مرحله است** → نیازمند یک سطح بالای مرحله.
3. **`wbs_phases` نمی‌تواند این نقش را بگیرد**، چون BD-05 صریحاً WBS Phase را از وزن جدا می‌کند و BD-06 به آن نقش دیگری می‌دهد.
