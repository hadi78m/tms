## 4) OD-1 — EVIDENCE (ساختار Membership)

### 4.1 آیا ساختار موجودی برای Project Membership هست؟ — **خیر (قطعی)**

شاهد ساختاری قطعی (read-only روی production `tms`):

```sql
SELECT table_name, string_agg(column_name, ', ')
FROM information_schema.columns
WHERE table_schema='public' AND column_name IN ('project_id','user_id')
GROUP BY table_name;

→ activity_logs: user_id
  comments: user_id
  modules: project_id
  sessions: user_id
  sla_events: user_id
  task_assignments: user_id
  tasks: project_id
  wbs_phases: project_id
```

**نتیجه:** **هیچ جدولی در کل اسکیما هم‌زمان `project_id` و `user_id` ندارد.** یعنی رابطهٔ Project↔User در مدل داده **به‌طور ساختاری غایب** است — نه pivot، نه ستون مالکیت، نه جدول generic assignment. این قوی‌ترین شاهد ممکن برای «Migration الزامی است» است.

تکمیل شواهد:

| جدول | رابطهٔ کاربری مرتبط | Project↔User؟ |
|---|---|---|
| `projects` | فقط `contract_id`(unique FK) · `contractor_id`(FK) | ❌ |
| `users` | فقط `contractor_id` (nullable FK→synced_contractors) | ❌ |
| `synced_contracts` | فقط `contractor_id` · `system_id` | ❌ |
| `synced_contractors` | شرکت پیمانکار (نه Employer) | ❌ |
| `task_assignments` | `task_id` · `user_id` · `assigned_by` | ❌ (**سطح Task** — FK به `tasks`) |
| `wbs_phases` | `project_id` + `supervisor_approved_by` (FK→users) | ⚠️ actor تأیید، نه تخصیص |
| `tasks` | `project_id` + `created_by` (FK→users) | ⚠️ سازنده، نه تخصیص |
| `modules` | `project_id` (بدون کاربر) | ❌ |

### 4.2 قرینهٔ معماری درون‌مخزن: `task_assignments` + `TaskAssignmentService`

این تنها ساختار **assignment تاریخی** در مخزن است. جدول کامل:

```php
// database/migrations/2026_09_17_140153_create_task_assignments_table.php
$table->id();
$table->foreignId('task_id')->constrained('tasks')->onDelete('restrict');
$table->foreignId('user_id')->constrained('users')->onDelete('restrict');
$table->foreignId('assigned_by')->constrained('users')->onDelete('restrict');
$table->timestampTz('assigned_at');
$table->timestampTz('ended_at')->nullable();
$table->string('reason', 255)->nullable();
$table->timestampTz('created_at')->useCurrent();
$table->timestampTz('updated_at')->useCurrent()->useCurrentOnUpdate();
$table->index(['user_id', 'assigned_at']);
$table->index('assigned_by');

DB::statement('CREATE UNIQUE INDEX idx_active_assignment ON task_assignments (task_id) WHERE ended_at IS NULL');
DB::statement('ALTER TABLE task_assignments ADD CONSTRAINT chk_ta_dates CHECK (ended_at IS NULL OR ended_at >= assigned_at)');
```

**چرا به‌عنوان قرینه قابل‌استفاده است (بخش‌های قابل‌انتقال):**

| جزء | قابل‌انتقال به Project Membership؟ | دلیل |
|---|:-:|---|
| بازهٔ تاریخی (`assigned_at`/`ended_at` nullable) | ✅ | همان معنای «تخصیص جاری + تخصیص تاریخی» |
| «فعال» مشتق = `ended_at IS NULL` | ✅ | تک‌حقیقت؛ سازگار با قاعدهٔ کاردینالیتی |
| partial unique index `WHERE ended_at IS NULL` | ✅ | تنها راه اثبات‌شدهٔ DB-level برای «حداکثر یک فعال» |
| CHECK `ended_at IS NULL OR ended_at >= assigned_at` | ✅ | جلوگیری از بازهٔ معکوس |
| Transaction + `lockForUpdate` + پایان دادن (نه حذف) + audit | ✅ | الگوی `TaskAssignmentService` |
| نگاشت `QueryException` → domain exception | ✅ | الگوی `TaskAssignmentRaceConditionException` |
| `assigned_by` + `reason` | ✅ | قابلیت ردیابی «چه‌کسی/چرا» |

**بخش‌هایی که Task-specific هستند و نباید کورکورانه کپی شوند:**

| جزء | هشدار |
|---|---|
| `foreignId('task_id')` | **سطح پروژه‌ای نمی‌شود**؛ تخصیص پروژه‌ای باید به `projects` متصل شود. (گزینهٔ H-E در recon دقیقاً به همین دلیل invalid است.) |
| ایندکس بدون predicate موقعیت: `(task_id) WHERE ended_at IS NULL` | در جدول generic، این predicate **همهٔ** موقعیت‌ها را قفل می‌کند و «چند Employer فعال» را ممنوع می‌کند؛ برای جدول generic **باید** با `position`/`assignment_type` محدود شود. |
| `SLA start/stop` وگذار status به `Assigned` | صرفاً منطق Task؛ هیچ قرینه‌ای برای Project وجود ندارد. |
| `TaskScopeService::assertCanAccess` (contractor-based) | scope پیمانکاری است، **نه** project scope — نباید با scope پروژه‌ای اشتباه شود. |
| `reason` اجباری/اختیاری بودن | در `task_assignments` **nullable** است؛ معنای «دلیل تغییر ناظر» باید تعیین شود (مالک). |

### 4.3 نقش/موقعیت (role/position) — آیا مفهوم project-specific وجود دارد؟

**قطعی: خیر.** مخزن فقط **یک** مفهوم نقش دارد و آن Spatie است:

| یافته | شاهد |
|---|---|
| `config/permission.php` → `'teams' => false` | نقش‌ها **سراسری**اند؛ یک کاربر نمی‌تواند per-project نقش متفاوت داشته باشد |
| نقش‌ها: admin · project_manager · supervisor · employer · contractor · management · viewer | `database/seeders/InitialTmsSeeder.php:31-38` |
| `task_assignments` هیچ ستون `role`/`position`/`assignment_type` ندارد | جدول §4.2 |
| هیچ ستون/جدولی با نام `position` · `assignment_type` · `project_role` در اسکیما نیست | جست‌وجوی schema + grep در `app/` |
| «نقش» فقط در دو جا ظاهر می‌شود: `model_has_roles` (Spatie) و اسنپ‌شات `actor_role` در audit | `DatabaseAuditService` docblock |

⇒ «project role» / «position» / «assignment type» **هیچ قرینه‌ای در مخزن ندارد**. ساخت آن = **invent** مگر مالک آن را تعیین کند.

**پاسخ صریح به پرسش ۳.۲ («آیا Supervisor باید به‌عنوان position عضویت مدل شود یا رابطه خودش Supervisor-specific باشد؟»):**

هر دو گزینه **repository-compatible** هستند و هیچ‌کدام از روی evidence **اجباری** نیست:

- **فقط position-column اجباری می‌شود اگر M-1 انتخاب شود** — چون:
  1. قاعدهٔ «حداکثر یک Supervisor فعال» نیازمند predicate در partial unique index است: `WHERE ended_at IS NULL AND position='supervisor'`.
  2. بدون ستون position، جدول generic نمی‌تواند «یک ناظر فعال» را از «چند Employer فعال» تفکیک کند.
  ⇒ این یک **استنتاج evidence-based** است، نه توصیهٔ معماری، و صرفاً **در صورت انتخاب M-1** معنا دارد.
- **در M-2** (جدول `project_supervisors`) predicate به `WHERE ended_at IS NULL` ساده می‌شود و ستون position بی‌معناست.

### 4.4 سازگاری با DEC-050

| قاعدهٔ DEC-050 | وضعیت |
|---|---|
| User → Role (Spatie) سراسری بماند | ✅ حفظ می‌شود (membership نقش سراسری را تغییر نمی‌دهد) |
| Role → Permission · User → Direct Permission | ✅ دست‌نخورده |
| Grant-only · صفر Deny | ✅ membership هیچ Deny ایجاد نمی‌کند |
| کاتالوگ سیستم‌کنترل · صفر dynamic route mapping | ✅ membership هیچ permission/route جدیدی نمی‌سازد |
| **مرز خطر** | اگر `position` در membership به یک سیستم مجوز موازی تبدیل شود ⇒ **نقض DEC-050**. position باید صرفاً **برچسب عملیاتی scope** باشد. |

نمونهٔ تشخیصی (conceptual — پیاده‌سازی نمی‌شود):

```text
کاربر U: permission = tasks.update  ✅  ·  position در Project X = supervisor  ← برچسب scope
⇒ tasks.update روی Project X مجاز می‌شود (Permission + Scope)
⇒ tasks.update روی Project Y (بدون membership) ممنوع می‌ماند (Permission ≠ Scope)
```

این **`INSUFFICIENT EVIDENCE`** برای شکل دقیق لینک است، نه برای نیاز به تصمیم.

### 6.4 هشدار تفکیک (بخش ۴.۲)

| `effective_from`/`effective_to` | **غایب** | — |

### 8.3 قرارداد نوع تاریخ/زمان

| کاربرد | نوع غالب مخزن | نمونه |
|---|---|---|
| لحظهٔ رویداد (assignment/approval/task lifecycle) | **`timestampTz`** | `assigned_at` · `ended_at` · `requested_at` · `acted_at` · `planned_start_at` · `submitted_at` · `approved_at` · `created_at` |
| بازهٔ تقویمی (قرارداد/پروژه/فاز) | **`date`** | `synced_contracts.start_date/end_date` · `projects.start_date/end_date` · `wbs_phases.start_date/end_date` |
| soft-delete | **`softDeletesTz()`** | `projects` · `users` · `tasks` · `synced_contracts` · … |

استثناها: `password_reset_tokens.created_at` و `jobs.failed_at` از `timestamp` استفاده می‌کنند (اسکلت پیش‌فرض Laravel، بی‌ارتباط با دامنه).

**نتیجهٔ evidence-based:** اگر Membership به‌عنوان **assignment history** مدل شود (هم‌خانوادهٔ `task_assignments`)، `timestampTz` قرینهٔ مستقیم دارد. اگر به‌عنوان **بازهٔ تقویمی** مدل شود (هم‌خانوادهٔ `projects`/`wbs_phases`)، `date` قرینه دارد. مثال مالک با تاریخ ساده (01/01/2026 → 30/06/2026) به سمت `date` اشاره دارد؛ الگوی `task_assignments` به سمت `timestampTz`. **قرینه مخزن هر دو را پشتیبانی می‌کند ⇒ انتخاب مالک است.**

پیامد فنی (برای تصمیم مالک): با `timestampTz`، «مرز روز» و timezone (Asia/Tehran) باید صریح تعریف شود؛ با `date`، معنای «روز پایان» (inclusive/exclusive) باید تعریف شود.

### 8.4 تخصیص آینده‌نگر (future-dated)

| جست‌وجو | یافته |
|---|---|
| تخصیص با `assigned_at` در آینده | **صفر** — `TaskAssignmentService:63` همیشه `now()` |
| effective/scheduled date | **صفر** — هیچ ستون `effective_*`/`scheduled_*` در کل اسکیما نیست |
| تنها CHECK زمانی | `chk_ta_dates`: `ended_at IS NULL OR ended_at >= assigned_at` (فقط بازهٔ معکوس را می‌گیرد) |

⇒ **هیچ قرینه‌ای برای تخصیص آینده‌نگر وجود ندارد.** اگر مالک آن را مجاز بداند، `ended_at IS NULL` **تنهایی کافی نیست** (یک تخصیص آینده فوراً «فعال» شمرده می‌شود) و predicate ایندکس/منطق سرویس باید time-aware شود. این یک **OWNER DECISION REQUIRED** است.

### 8.5 مکانیزم کاردینالیتی — تأیید evidence

### 18.6 Supervisor Cardinality (تأیید مجدد — بدون تغییر)

**حداکثر یک Supervisor فعال در هر Project.** تخصیص تاریخی **نامحدود**. مثال معتبر:

```text

  Supervisor A   started 2026-01-01 · ended 2026-06-30   ← historical (حذف نمی‌شود)
  Supervisor B   started 2026-07-01 · ended NULL         ← active
```

نامعتبر: دو رکورد با `ended_at IS NULL` برای همان Project. **قید دیتابیسی هنوز پیاده‌سازی نشده** — مکانیزم (partial unique index + service، مطابق قرینهٔ C-4) در دروازهٔ پیاده‌سازی تعیین و اجرا می‌شود.

### 18.7 Enforcement Architecture (بدون تغییر)

DR-11-1 / ③ = **G-C** با **Query Scope** پشتیبان. تفکیک مسئولیت:

| لایه | مسئولیت |
|---|---|
| **Middleware** | coarse-grained area/role access (مکانیزم‌های `role:` موجود معتبر می‌مانند) |
| **Policy** | Resource Authorization |
| **Query Scope** | جلوگیری از retrieval منابع پروژه‌ای غیرمجاز |
| **Service Guard** | Business Invariants |

**Permission ≠ Project Scope** (permission دسترسی به همهٔ پروژه‌ها نمی‌دهد) · Policy جای Service Guard را نمی‌گیرد · Project Scope از Business Invariants عبور نمی‌کند. **DEC-049 (Tasks → Approvals → Modules → Wbs) و DEC-050 بدون تغییر** — هیچ‌یک از این migrationها در این Task آغاز نمی‌شود.
