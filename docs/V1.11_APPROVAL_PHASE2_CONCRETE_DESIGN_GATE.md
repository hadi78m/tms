## 4. Resource Scope Resolution Design (DEC-056)

### Task approvals
```text
ApprovalPolicy::createTechnical(User, Task) / createFinal(User, Task)
  → role check (admin|supervisor / admin|employer)
  → permission check (technical_approval / final_approval)   [DEC-050: grant-only]
  → ProjectScopeService::canAccessProject($task->project, $user)
```
- Relationship: `Task.project()` exists, non-nullable in practice (`tasks.project_id` constrained) — reliable direct path.
- **create-at-target**: the bound `{task}` IS the resource — no lookup of a second model occurs (unlike dependencies), so no second-surface enumeration risk.

### Stage progress
```text
StageProgressApprovalPolicy::propose/adjust/supersede(User, Stage|Approval) / decide(User, Approval)
  → role-consistency with route middleware (informational — mw remains authoritative)
  → ProjectScopeService::canAccessProject(resolveProject(...), $user)
```
- Resolution paths (evidence):
  - propose: `ModuleStage $stage` (bound) → `ModuleStage.module_id → Module.project_id` — one hop, reliable.
  - adjust/supersede/decide: `StageProgressApproval` carries **denormalized `module_id`** → `Module.project_id` — **one hop** (no need to trust `module_stage_id → module` chain; `supersede()` already cross-checks `module_stage_id` consistency).
- Nullable audit: `ModuleStage.module_id` is part of the V1.9 DEC-021 derivation pattern — treated as NOT NULL by design; Policy must still fail-closed (deny) if the relation fails to resolve.
- **No alternate project path exists** for either entity (verified: no other FK chain reaches Project).
- **Direct-ID enumeration**: bound-model 404 (ModelNotFoundException → standard page, no payload) — after Phase 2, a foreign ID resolves *then* is scope-denied 403; response carries no resource identity (Phase 1 pattern).

## 6. Policy / Service Boundary (DEC-058 — no duplication)

**Policy (new, both):** Role · Permission (task approvals only) · Project Scope (via `ProjectScopeService` — never local) · resource relationship resolution · fail-closed on unresolvable relation.

**Service (unchanged owners):** `ApprovalService` — contractor-null guard, task-already-approved, tier→state preconditions, transactional audit. `StageProgressApprovalService` — mode-based proposer authorization, supervisor-only decide, one-active-pending, cumulative ceiling (parent-lock, DEC-026), approved ≤ proposed, 0 < proposed ≤ 100, supersede-chain linearity (T-1, DEC-027), immutability, audit. Race conditions (lockForUpdate patterns) stay in services.

Rule: a Policy denial must short-circuit *before* the service; a service exception must never be masked as authorization success. No rule may appear in both layers.

## 7. Direct Grant Analysis (DEC-050 / DEC-059 — explicit)

- Supervisor + **direct** `final_approval` grant → **NO / DENY** (role `admin|employer` required).
- Employer + **direct** `technical_approval` grant → **NO / DENY** (role `admin|supervisor` required).
- Management/Viewer/PM/Contractor + any direct approval grant → **NO / DENY**.
- Admin passes role+permission naturally; scope-unrestricted by DEC-048 (scope bypass only — never permission/invariant bypass).
- Rationale recorded in gate: `Permission ≠ Role ≠ Project Scope`; Direct grants are Grant-only (no Deny mechanism); DEC-059 makes role boundary non-bypassable by design in the Policy (same pattern as `TaskPolicy::create` after DEC-054/055).

## 8. Employer Scope Dependency (DEC-057 — OPEN)

Repository audit (2026-09-30) — exhaustive relation check:

| Relation candidate | Evidence | Verdict |
|---|---|---|
