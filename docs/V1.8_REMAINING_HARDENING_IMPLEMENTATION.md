## 2. R-3 — Active/Superseded Consolidation

### 2.1 Definitions found (re-inspection — R-3.1)

جست‌وجوی مجدد کل `app/` با الگوهای `scopeActive` · `isSuperseded` · `approvedQuery` · `active approval` — همان ۵ تعریف + `Module::scopeActive()` هم‌نامِ غیرمرتبط. **هیچ موردی از دست رفته نبود** و هیچ تعریف ششمی پیدا نشد. مصرف‌کنندگان بیرونی: `ModuleStage::approvedWeight()` و `remainingWeight()` از `approvedQuery()`؛ تست‌ها از `isSuperseded()` مدل — همه از مسیرهای کنسولیدیه‌شده عبور می‌کنند.

### 2.2 Chosen refactor (smallest safe — R-3.6)

| فایل | قبل | بعد |
|---|---|---|
| `ModuleStage::approvedQuery()` | کپی حرفِیِ `scopeActive()` (where + whereNotExists دستی) | `$this->approvals()->active()` — delegation به تعریف واحد |
| `StageProgressApprovalService::isSuperseded()` | کپی حرفِیِ `StageProgressApproval::isSuperseded()` (استandalone query) | `$approval->isSuperseded()` — delegation به مدل |

**انجام نشد (عمداً):**
- `pendingQuery()` — فیلتر status آن (`pending`) **عمداً** با `active` متفاوت است؛ ادغام آن با Active معناشناسی را عوض می‌کرد (ممنوع). تنها جزء مشترک (NOT EXISTS) به‌تنهایی abstraction ای نمی‌سازد که ارزشش بیشتر از هزینه‌اش باشد («Duplication کوچک بهتر از abstraction اشتباه است»).
- Base Class / Trait / Helper — rejected: برای حذف دو کپی، coupling اضافی می‌ساخت.

### 2.3 Why the abstraction is safe

هر دو delegation، بدنه‌ای را فراخوانی می‌کنند که **کپی حرفِیِ** خودِ refactorشده بود (اثبات هم‌ارزی در Reconnaissance §۱.۲):
- `approvals()->active()` → همان `where status='approved'` + همان `whereNotExists(superseding.supersedes_approval_id = id)` — روی همان relation (`hasMany` با همان کلید خارجی `module_stage_id`).
- `$approval->isSuperseded()` → `supersededBy()->exists()` = `EXISTS(supersedes_approval_id = id)` — دقیقاً همان query قبلی Service.
هیچ transaction/locking/authorization/audit مسیری از این دو متد عبور نمی‌کند که تغییر نکرده باشد؛ امضای متدها و خروجی‌ها یکسان ماندند.

### 2.4 Why `Module::scopeActive()` remained separate

`Module::scopeActive()` → `status = 'active'` (وضعیت چرخهٔ حیات Module طبق `ModuleStatus` enum) — **مفهومی مستقل** از «Active Approval» (`approved` + بدون جانشین). هم‌نامی تصادفی است؛ تغییر نام آن صرفاً به‌خاطر تشابه، خوانایی دامنه را خراب می‌کند. **ثبت شد: naming collision — semantic distinction (R-3.4).**

```text
phpunit.xml ....... DB_CONNECTION=pgsql · DB_DATABASE=tms_testing — صریح (Host/User/Pass از .env ارث)
.env.testing ...... وجود ندارد

tests/TestCase.php  قبلاً خالی بود

DatabaseMigrations / DatabaseTruncation / LazilyRefreshDatabase ... استفاده نشده‌اند
composer scripts ... "test" = config:clear + artisan test؛ هیچ destructive script ای تعریف نشده
AGENTS.md ... قاعدهٔ عمومی destructive confirmation دارد اما به tms/tms_testing اشاره نمی‌کند
docs/ ... فقط سابقهٔ ENV-1 («بازسازی tms_testing با مجوز صریح مالک»)
```

### 3.2 Gap

`RefreshDatabase` مسیر reset فریمورک است اما هیچ سازوکاری جلوی اشارهٔ Suite به دیتابیس اشتباه را نمی‌گرفت؛ دستورات artisan دستی هم گیت مکتوب نداشتند.

### 3.3 Implementation (دو لایه — با تفکیک صادقانهٔ سطح محافظت)

**لایهٔ ۱ — ENFORCED (کد):** `tests/TestCase.php` — T-6 Safety Gate. در `setUp()` هر تست، **نام واقعی دیتابیسِ متصل** (`DB::connection(config('database.default'))->getDatabaseName()`) خوانده می‌شود؛ اگر به `testing` ختم نشود، Suite فوراً fail می‌شود — **قبل از** اینکه RefreshDatabase فرصت بازسازی داشته باشد. تشخیص بر اساس نام دیتابیسِ واقعیِ همان connection ای است که reset استفاده می‌کند — نه یک flag دستی (R-6.4: قابل‌اعتماد است، چون همان منبع حقیقتِ فریمورک را می‌خواند).

**لایهٔ ۲ — DOCUMENTED:** `docs/DATABASE_SAFETY.md` — گیت عملیاتی برای دستورات artisan دستی (Safe / Potentially destructive + قاعدهٔ بررسی `migrate:status` قبل از هر destructive). دستورات دستی از TestCase عبور نمی‌کنند، پس این لایه **صادقانه فقط DOCUMENTED** است.

### 3.4 Exact protection provided

```text
ENFORCED:    php artisan test (کل Suite) → هرگز RefreshDatabase روی غیر-testing اجرا نمی‌کند
DOCUMENTED:  migrate:fresh / refresh / reset / db:wipe / db:seed → checklist عملیاتی + قاعدهٔ مجوز مالک
```

### 3.5 Limitations (صادقانه)

دستورات artisan دستی enforce نمی‌شوند (T-6.4/T-6.6 رعایت شد — ادعای جعلی ثبت نشد). اگر در آینده توسعه‌دهنده `DB_DATABASE` را به نام غیر-testing تغییر دهد، گارد Suite را **متوقف می‌کند** (رفتار صحیح). CI هنوز وجود ندارد (T-7 — فاز بعدی).
