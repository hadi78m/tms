## 2. T-3 — `task_rejected`

### 2.1 مسیرهای رد (کامل، بازرسی کد)

| # | مسیر | مالک | رویداد Audit ثبت‌شده |
|---|---|---|---|
| 1 | رد فنی (Supervisor · `under_review → needs_rework`) | `ApprovalService::recordTechnicalApproval()` | `task_approval_recorded` (new_values شامل status + Approval record کامل) |
| 2 | رد نهایی (Employer · `supervisor_approved → needs_rework`) | `ApprovalService::recordFinalApproval()` | `task_approval_recorded` + `task_final_approved` |
| 3 | نیاز به اصلاح عمومی | `TaskService::needsRework()` | `task_status_changed` + metadata `reason` |
| 4 | رد درخواست تغییر وزن | `WeightChangeRequestService::rejectRequest()` | `task_weight_change_rejected` (رویداد اختصاصی — الگوی موجود) |

### 2.2 تحلیل Bypass

`DatabaseAuditService` (DEC-011) همگام و تراکنشی است، درون `DB::transaction` صدا زده می‌شود و **failure آن هرگز swallow نمی‌شود** ⇒ اگر audit نوشته نشود، خود عملیات رد هم rollback می‌شود. **هیچ مسیری bypass ندارد.** همهٔ ردها inside same transaction auditable هستند.

### 2.3 آیا رویداد مستقل اطلاعات جدیدی می‌دهد؟

خیر — از نظر داده. همان اطلاعات (actor، status قبلی/جدید، comment، sequence، acted_at) هم‌اکنون در `task_approval_recorded` + ردیف `approvals` با `status = needs_rework` موجود است. رویداد مستقل فقط **قابلیت فیلتر/جست‌وجوی راحت‌تر** می‌دهد (گزارش «همهٔ ردها» بدون parse کردن `new_values`) — یک ارزش گزارش‌گیری، نه اطلاعات جدید.

### 2.4 پیاده‌سازی چه می‌خواهد؟

**فقط کد + تست** — صفر Schema · صفر Migration · صفر Enum. نقطهٔ صادر: بلافاصله پس از `task_approval_recorded` در `recordTechnicalApproval()` و `recordFinalApproval()`، درون همان transaction، با شرط `$status === ApprovalStatus::NeedsRework`.

### 2.5 آیا سند معتبری الزامش کرده؟

**خیر.** جست‌وجوی `docs/` و `project_context/`: تنها مرجع `M-5` در `V1.8_MIGRATION_REVIEW_REPORT.md` است که خودش می‌گوید اگر مرجع کسب‌وکاری رویداد مستقل بخواهد باید فهرست §۸.۳ اصلاح شود — یعنی مرجع کسب‌وکاری «لازم است» نه «موجود است».

## 4. T-5 — Project Soft Delete Integrity

### 4.1 تفکیک سه سطح (طبق دستور فاز)

**الف — DB hard-delete protection:** ✅ موجود و اثبات‌شده. `projects.contract_id UNIQUE` + همهٔ فرزندان (`tasks.project_id`, `modules.project_id`, `wbs_phases.project_id`) با `ON DELETE RESTRICT` ⇒ hard delete یک Project دارای فرزند، در سطح PostgreSQL مسدود است. (Migrations 1–23 immutable — دست نخوردند.)

**ب — Application soft-delete policy:** ❌ **قاعده‌ای وجود ندارد — و هیچ مسیر حذف هم وجود ندارد.** یافته‌های بازرسی:
- هیچ `ProjectService` ای وجود ندارد.
- هیچ route/controller/action ای Project را حذف نمی‌کند (grep کامل `app/` + `routes/`: صفر نتیجه).
- `Project` از Eloquent `SoftDeletes` استفاده می‌کند (سازهٔ فریمورک)، اما هیچ‌جای کد آن را فراخوانی نمی‌کند.
- هیچ DEC/BD ای به «حذف نرم Project با Module فعال» اشاره نمی‌کند.

**ج — Restore policy:** ❌ قاعده‌ای وجود ندارد؛ اما چون هیچ مسیر حذف نرمی وجود ندارد، restore عملاً در دسترس نیست و هیچ state ناسازگاری قابل‌ایجاد نیست.

### 4.2 آیا قاعدهٔ معتبری موجود است؟

**خیر.** `ModuleService::archive()` و `restore()` (با invariant `SUM=100` و `DEC-024`) برای **Module** قاعده دارند؛ برای **Project** هیچ معادل مستندشده‌ای وجود ندارد.

### 4.3 رده‌بندی نهایی

```text
T-5 = OWNER DECISION REQUIRED / DEFERRED
```

قاعدهٔ «آیا Project با Module فعال قابل حذف نرم است؟» یک تصمیم کسب‌وکاری است که مالک باید بدهد؛ عوامل تصمیم: آیا اصلاً مسیر حذف Project در محصول وجود خواهد داشت؟ آیا بله، آیا حذف با Module فعال ممنوع است یا باید با rebalance همراه شود؟ تا آن زمان: **NO CODE CHANGE** (و هیچ مسیر حذف فعلی وجود ندارد که enforce در آن لازم باشد).

## 5. T-7 — CI / Environment Safety

### 5.1 یافته‌ها

| مورد | وضعیت |
|---|---|
| `.github/` / `.gitlab-ci.yml` / `bitbucket-pipelines.yml` | ❌ هیچ‌کدام وجود ندارند — **CI نیست** |
| Tests on PostgreSQL? | ✅ بله — `phpunit.xml`: `DB_CONNECTION=pgsql` + `DB_DATABASE=tms_testing` |
| CI could point to `tms`? | فعلاً نا applicable (CI وجود ندارد)؛ اگر ساخته شود، سد موجود `Tests\TestCase` (T-6 gate) هر اجرای Suite روی غیر-`*testing` را fail می‌کند — **سد ساختاری از قبل فعال است** |
| CI bootstrap verifies DB name? | n/a — ولی گارد TestCase این نقش را برای Suite ایفا می‌کند |
| PostgreSQL env vars documented? | نیمه — `DATABASE_SAFETY.md` مدل DB را توضیح می‌دهد؛ متغیرهای CI فهرست نشده‌اند (پایین آمده) |
| `.env.example` conflicts with doctrine? | `DB_CONNECTION=sqlite` با بقیهٔ DB خطوط کامنت — این **development default** فریمورک است؛ doctrine testing از `phpunit.xml` می‌آید و production از `.env` واقعی. سه لایه متمایز‌اند و تعارض عملی وجود ندارد. تغییر صرفاً زیبایی‌شناختی انجام نشد (طبق قانون فاز) |
| Adding CI in scope? | خیر — این فاز پیاده‌سازی CI را مجاز نکرده است |
