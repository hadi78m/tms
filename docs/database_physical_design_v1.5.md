## 2. Global Conventions & Engine Strategy
- **Target Engine:** PostgreSQL
- **Primary Key Strategy:** `BIGINT GENERATED BY DEFAULT AS IDENTITY`
- **Timestamp Strategy:** 
  - زمان‌های سیستمی: `TIMESTAMPTZ` (دیتابیس در UTC ذخیره می‌کند).
  - تاریخ‌های تقویمی: `DATE`
- **ON UPDATE Policy:** `ON UPDATE NO ACTION` برای تمامی کلیدهای خارجی (برای جلوگیری از تغییرات زنجیره‌ای خطرناک شناسه اصلی).

## 3. SLA Lifecycle Semantics (فریز شده)

### Response SLA
- **START:** `task assigned` (زمان Assigned شدن تسک)
- **STOP:** `first valid contractor response` (اولین پاسخ معتبر پیمانکار)
  
**تعریف First Valid Contractor Response:**
اولین Action معتبر ثبت‌شده توسط کاربر Contractor روی Task پس از Assignment که نشان‌دهنده شروع رسیدگی Contractor به Task باشد.
**اکشن‌های معتبر (Valid Responses):**
1. تغییر وضعیت از `assigned` به `in_progress`
2. ثبت Comment توسط پیمانکار (Contractor Comment)
3. آپلود داکیومنت توسط پیمانکار (Contractor Document Upload)

*موارد نامعتبر (Response محسوب نمی‌شوند):* ایجاد تسک، Assignment مجدد، Final Submission، کارهای سوپروایزر یا اپراتور و تایید نهایی.

### Resolution SLA
- **START:** `task assigned` (زمان Assigned شدن تسک)
- **STOP:** `submitted_for_review`
  
*دلیل:* این SLA صرفا زمان عملکرد پیمانکار را می‌سنجد. زمان‌های Review یا Approve سازمان نباید در کارکرد پیمانکار محاسبه شود.

### SLA Records vs SLA Events (Architectural Note)
- **`sla_records`:** نمایانگر Current / Computed SLA State است. این جدول مقادیر محاسبه شده و وضعیت فعلی تایمرها را دارد.
- **`sla_events`:** نمایانگر Immutable SLA Event History است. این جدول شامل لاگ تغییرات خطی (`start`, `pause`, `resume`, `stop`, `breach`) بوده و منبع اصلی History است.

## 4. Controlled Denormalization Rules
آی‌دی‌های `contract_id` و `contractor_id` در جداول پایین‌دستی مانند `projects` و `tasks` به جهت سرعت در Scope کردن Isolation پیمانکاران ذخیره می‌شوند.
**قانون اعتبارسنجی:** مقادیر Denormalized هرگز از ورودی کاربر خوانده نمی‌شوند، بلکه Application Layer با اعتبارسنجی والد، آن‌ها را درج می‌کند.

## 5. Index Coverage & FK Performance Matrix
> PostgreSQL برای Foreign Keyهای Child بهصورت خودکار Index ایجاد نمیکند؛ بنابراین Indexing باید آگاهانه و بر اساس Query Pattern و نیازهای Performance تعریف شود.

وضعیت هر Foreign Key در دیتابیس بر اساس کدهای زیر تعیین شده است:
- **A — Dedicated Index:** یک ایندکس مختص به همین فیلد وجود دارد.
- **B — Covered by Composite Index:** در یک ایندکس ترکیبی، به عنوان کلید پیشرو (Leading) یا اصلی پوشش داده شده است.
- **C — Intentionally Not Indexed:** به صورت عمدی در V1.5 ایندکسی ندارد (مثلا بار کوئری مستقل روی آن کم است یا Cardinality نامناسبی دارد).

## 6. Table-by-Table Final Specification & Constraints

*(فقط ویژگی‌های اختصاصی و محدودیت‌ها لیست شده است، فیلدهای عمومی مشابه جداول مرسوم می‌باشد)*

### 6.1 WBS Phases
- **Application Business Rule (Weight):** مجموع Weight فازهای یک Project باید `100` باشد. این قاعده صرفاً در لایه **Application / Service Layer Validation** هندل می‌شود و در دیتابیس قید نمیشود.

### 6.2 Task Dependencies
- **Columns:** `id`, `predecessor_task_id`, `successor_task_id`, `dependency_type`, `created_by`, `created_at`.
- **Primary Key:** `id`
- **Unique Constraint:** `UNIQUE (predecessor_task_id, successor_task_id, dependency_type)`
- **Check Constraints:** 
  - `CHECK (predecessor_task_id <> successor_task_id)`
  - `CHECK (dependency_type = 'fs')`
- **FK Rules (Historical Preservation):**
  - `predecessor_task_id -> tasks.id ON DELETE RESTRICT ON UPDATE NO ACTION`
  - `successor_task_id -> tasks.id ON DELETE RESTRICT ON UPDATE NO ACTION`
  - `created_by -> users.id ON DELETE RESTRICT ON UPDATE NO ACTION`
- **Immutable:** No `updated_at`, No `deleted_at`. Business layer cannot Hard Delete.

## 7. Historical Preservation (فریز شده)
**Main System = Source of Truth**, ولی **TMS = Historical Record Keeper**.
هیچ‌کدام از عملیات‌های حذف یا Deactivate در سیستم مرکزی نباید History تسک‌ها، اوزان، SLA و عملکرد را در TMS تخریب کند. این یعنی حذف‌ها فقط ماهیت Soft Delete دارند.
