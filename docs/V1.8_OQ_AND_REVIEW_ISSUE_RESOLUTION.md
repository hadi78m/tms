## ۷. `OQ-02` — چند ماژول بدون `code` مجاز باشد؟

### ۷.۱ متن دقیق پرسش

| منبع | متن |
|---|---|
| `V1.8_DETAILED_SCHEMA_DESIGN.md:1543` | «`modules.code` NULL: چند ماژول بدون code مجاز باشد؟» — توصیهٔ سند: «بله — با Partial Unique Index اگر محدودیت لازم است» |
| `V1.8_DETAILED_SCHEMA_DESIGN.md:212` (§۴.۱) | «PostgreSQL مقادیر `NULL` را در UNIQUE متمایز می‌شمارد، پس چند ماژول بدون `code` با هم تضاد ندارند. اگر این رفتار نامطلوب است، باید Partial Unique Index استفاده شود» |
| `V1.8_MIGRATION_REVIEW_CHECKLIST.md:64` | «چند ماژول بدون `code` مجاز باشد؟ | 🟡 باز» |
| `V1.8_RECONCILIATION_AND_MIGRATION_GATE.md:717` | «`OQ-02` 🟢 موکول — NULL بودن `modules.code`» |

### ۷.۲ چرا باز شد

طراحی `UNIQUE (project_id, code)` را با `code` **NULLABLE** ترکیب می‌کند. در PostgreSQL، `NULL` با هیچ مقدار دیگری «برابر» نیست، پس ردیف‌های با `code = NULL` از دید UNIQUE **متمایز** شمرده می‌شوند. یعنی قاعدهٔ واقعی چنین است:

```text
در محدودهٔ هر project:
  • اگر code مقدار داشته باشد → باید یکتا باشد
  • ماژولهای با code = NULL → نامحدود و بیقید
```

این دقیقاً معنای «Partial Unique Index روی `code IS NOT NULL`» است — منتها UNIQUE مرکب فعلی **همین را از قبل می‌دهد** و نیازی به Index دوم ندارد.

### ۷.۳ شاهد Repository

| شاهد | جزئیات | دلالت |
|---|---|---|
| ستون `code` در Repository | فقط `synced_systems.code` و `synced_contractors.code` — **هر دو NOT NULL و بدون UNIQUE** | **صفر پیشینهٔ مستقیم** برای «code اختیاری + یکتا» |
| UNIQUEهای مرکب موجود | `(source_system, external_id)` ×۳ · `(predecessor_task_id, successor_task_id, dependency_type)` · `(contract_id, contractor_id, period_start, period_end)` | الگوی نام‌گذاری: `idx_*_unique` یا `foreignId()->unique()` — **هیچ‌کدام nullable نیستند** |
| UNIQUE با ستون nullable | `permission_tables` (یک حالت) — رفتار PostgreSQL پذیرفته شده | الگوی «UNIQUE با nullable» در Repository سابقه دارد |
| `projects` | `contract_id` UNIQUE (NOT NULL) · صفر ستون `code` | Module تنها موجودیت با `code` خواهد بود |
| `wbs_phases` | صفر ستون `code` | — |

### ۷.۴ گزینه‌ها و پیامدها

| گزینه | محتوا | پیامد |
|---|---|---|
| **A** | **همان طراحی فعلی:** `code` NULLABLE + `UNIQUE (project_id, code)` | ماژول‌های بدون code نامحدود · codeهای موجود یکتا · **صفر Migration اضافه** · رفتار PostgreSQL کاملاً مستندشده |
| **B** | `code` NULLABLE + **Partial Unique Index** `WHERE code IS NOT NULL` | **نتیجهٔ عملی برابر با A** (PostgreSQL در `UNIQUE` متعارف هم NULLها را متمایز می‌شمارد) → **Index اضافه و بی‌فایده**، مگر آنکه بخواهیم Index کوچک‌تر باشد |
| **C** | `code` **NOT NULL** + `UNIQUE (project_id, code)` | UNIQUE کاملاً معنادار · نمایش/تولید اجباری code | هر ماژول باید code داشته باشد — یک قاعدهٔ کسب‌وکاری جدید که هیچ سندی آن را نخواسته؛ Front-end/Service باید code تولید کند |
| **D** | UNIQUE **حذف** و یکتا بودن `code` در Service | انعطاف کامل | تکرار code در DB ممکن می‌شود — ضعیف‌تر از امروز |

### ۷.۵ توصیهٔ فنی

```text

```

**توصیه: گزینهٔ A — طراحی فعلی حفظ شود. گزینهٔ B هیچ اثر رفتاری ندارد و نباید اضافه شود.**

دلیل فنی صریح: `UNIQUE (project_id, code)` در PostgreSQL **از قبل** یعنی «codeهای غیرتهی در هر پروژه یکتا باشند»؛ افزودن Partial Unique Index روی `code IS NOT NULL` **معنای جدیدی اضافه نمی‌کند**. گزینهٔ C **قاعدهٔ کسب‌وکاری جدید** می‌سازد و مجاز نیست بدون درخواست صریح.

**اصلاح مستنداتی لازم:** جملهٔ سند (§۴.۱) که می‌گوید «اگر این رفتار نامطلوب است، باید Partial Unique Index استفاده شود» از نظر فنی **گمراه‌کننده** است و باید به «رفتار فعلی UNIQUE دقیقاً همان Partial Unique روی codeهای غیرتهی است؛ در صورت نیاز به *الزام* code، باید `NOT NULL` شد (تصمیم جداگانه)» تغییر کند. **طبقه‌بندی:** **جزئیات پیاده‌سازی + تفسیر PostgreSQL** — تصمیم مالک پروژه لازم **نیست**؛ فقط **تأیید** توصیه‌شده. **قابل موکول نیست** فقط از این جهت که `U-01` را در `M-01` تعیین می‌کند — ولی **تغییری در طراحی فعلی ایجاد نمی‌کند**، پس مانع نیست.

## ۸. `H-1` — اصلاح طراحی سقف تأیید تجمعی

### ۸.۱ مسئلهٔ فنی (تأییدشده)

```sql
-- سند Schema §۶.۵ (خواندهشده)
SELECT COALESCE(SUM(approved_amount), 0)
  FROM stage_progress_approvals
 WHERE module_stage_id = ? AND status = 'approved'
   FOR UPDATE;
```

PostgreSQL این کوئری را رد می‌کند:

```text
ERROR:  FOR UPDATE is not allowed with aggregate functions
```

دلیل: `FOR UPDATE` ردیف‌های **مبنای** کوئری را قفل می‌کند؛ در کوئری تجمیعی ردیف مبنایی برای قفل وجود ندارد (نتیجه یک ردیف تجمیعی است). این محدودیت در PostgreSQL برای **همهٔ** توابع تجمیعی (`SUM`, `COUNT`, `MIN`, `MAX`, `AVG`, …) و همچنین `GROUP BY` + `FOR UPDATE` اعمال می‌شود.

> ⚠️ **محدودیت اعتبارسنجی این فاز:** چون اجرای هر DDL/DML ممنوع است، این یافته **از مستندات PostgreSQL و ساختار SQL استنتاج شده** و **با اجرا تأیید نشده است**. راهبرد جدید هم به‌صورت SQL نوشته شده اما **اجرا نشده** — اجرای آن به فاز Migration Implementation موکول است.

### ۸.۲ تحلیل گزینه‌ها (A..E)

#### گزینهٔ A — قفل ردیف‌های زیربنایی

```sql
SELECT id FROM stage_progress_approvals
 WHERE module_stage_id = ? AND status = 'approved'
   FOR UPDATE;                        -- معتبر است (بدون تجمیع)
-- سپس مجموع در PHP/کوئری دوم محاسبه شود
```

| پرسش | پاسخ |
|---|---|
| چه ردیف‌هایی قفل می‌شوند؟ | فقط ردیف‌هایی که **در لحظهٔ اجرا** با شرط مطابقت دارند |
| در برابر **INSERT** همزمان محافظت می‌کند؟ | ❌ **خیر** — در `READ COMMITTED` هیچ قفل predicate وجود ندارد؛ ردیف جدید قابل مشاهده/قفل نیست (Phantom) |
| اگر **صفر** ردیف تأییدشده وجود داشته باشد؟ | ❌ هیچ چیزی قفل نمی‌شود → دو تراکنش همزمان می‌توانند هر دو عبور کنند |
| مسابقهٔ زمانی را می‌بندد؟ | ❌ **نه** |

→ **رد به‌عنوان راهبرد اصلی.** (نمی‌تواند سقف را تضمین کند؛ دقیقاً همان حالتی که خطرناک است — اولین تأیید.)

#### گزینهٔ B — قفل ردیف والد `module_stages` ← **پیشنهاد اصلی**

```sql
-- داخل DB::transaction
SELECT id, weight FROM module_stages WHERE id = ? FOR UPDATE;   -- ① قفل مخرج
SELECT COALESCE(SUM(approved_amount), 0)                         -- ② بدون FOR UPDATE
  FROM stage_progress_approvals
 WHERE module_stage_id = ? AND status = 'approved';
```

| معیار | ارزیابی |
|---|---|
| چه چیزی قفل می‌شود؟ | یک ردیف قطعی و **همیشه موجود** (`module_stages.id`) — مستقل از اینکه چند ردیف تأیید وجود دارد |
| همزمانی | ✅ اگر **هر** مسیر کدی که ردیف‌های `stage_progress_approvals` را درج/تغییر می‌دهد **ابتدا** قفل والد را بگیرد، همهٔ نویسندگان یک Stage روی همان ردیف **سریال** می‌شوند؛ پس SUM دوم همیشه مقدار به‌روز را می‌بیند |
| سادگی | ✅ حداکثر — `ModuleStage::whereKey($id)->lockForUpdate()->first()` |
| درستی | ✅ **مشروط** به یک قاعدهٔ اجباری: «هیچ نوشتنی روی تأییدهای یک Stage بدون قفل والد مجاز نیست» |
| اثر جانبی | قفل یک ردیف واحد به‌ازای هر Stage → تأییدهای همزمان **روی Stageهای مختلف** با هم تضاد ندارند (بدون گلوگاه سراسری) |
| هم‌خوانی با Repository | ✅ **دقیقاً** الگوی `WeightChangeRequestService` (`lockForUpdate()` داخل `DB::transaction`) |
| مرز تراکنش | ✅ `lockForUpdate()` فقط **داخل** `DB::transaction` معنا دارد؛ اگر بیرون اجرا شود قفل بلافاصله آزاد می‌شود |

→ **راهبرد پیشنهادی اصلی.**

#### گزینهٔ C — `pg_advisory_xact_lock`

```sql
SELECT pg_advisory_xact_lock(<key>);   -- key مشتق از module_stage_id
```

| معیار | ارزیابی |
|---|---|
| چرا سریال می‌کند؟ | قفل مشورتی سطح-تراکنش متناظر با یک «منبع تعریف‌شده توسط برنامه»؛ دو تراکنش با کلید یکسان، یکی منتظر می‌ماند |
| عمر قفل | ✅ **خودکار در پایان تراکنش آزاد می‌شود** (`xact`) — بدون نشتی قفل |
| Deadlock | ⚠️ اگر ترتیبی جز کلید مشورتی → قفل والد یا برعکس وجود داشته باشد، امکان Deadlock؛ تشخیص سخت‌تر (نامرئی برای ORM) |
| وابستگی اپلیکیشن | ⚠️ Laravel API درجه‌اول ندارد → **الزاماً SQL خام** |
| قابلیت حمل | ⚠️ مخصوص PostgreSQL؛ اگر روزی موتور عوض شود، بی‌اثر می‌شود |
| کشف‌پذیری | 🔴 **مهم‌ترین ضعف:** قفل مشورتی در مدل قفل عادی دیتابیس دیده نمی‌شود؛ اگر یک مسیر کد آن را فراموش کند، **هیچ خطایی رخ نمی‌دهد** و سکوت، درستی را می‌شکند |

→ **راهبرد جانشین (Fallback)** — همان تضمین B را دارد اما با شفافیت کمتر. فقط اگر لازم شد Stageای قفل شود که **ردیف والد قابل قفل ندارد** (اینجا غیرممکن است) توجیه می‌شود.

#### گزینهٔ D — `SERIALIZABLE`

| معیار | ارزیابی |
|---|---|
| آیا به‌تنهایی سقف را تضمین می‌کند؟ | ✅ بله — SSI ساختار خطرناک (rw-dependency) را تشخیص می‌دهد |
| الزام Retry | 🔴 **بله** — شکست سریال‌سازی با `SQLSTATE 40001` رخ می‌دهد و باید **دوباره تلاش** شود |
| استثنای مورد انتظار | `SerializationFailure` / خطای 40001 که Laravel در قالب `QueryException` سطح می‌دهد → نیازمند Wrapper اختصاصی در هر مسیر نوشتن |
| پیچیدگی اپلیکیشن | 🟠 بالا — الگوی Retry باید در Service، Controller و Jobها تکرار شود (`DB::transaction($cb, $attempts)` فقط Deadlock را Retry می‌کند، نه 40001 را در همهٔ نسخه‌ها) |
| مقایسه با قفل ردیف | 🔴 **نامناسب‌تر** برای این پروژه: مسیر تأیید درصدی کم‌ترافیک است؛ هزینهٔ پیچیدگی و شکست‌های تصادفی بزرگ‌تر از سود است |

→ **رد به‌عنوان راهبرد اصلی.** (به‌عنوان Fallback برای Jobهای Import انبوه قابل بازنگری است.)

#### گزینهٔ E — ردیف حالت تجمیعی جداگانه

اگر ردیفی مثل `module_stages.approved_total` نگه داشته شود، سقف با یک CHECK ساده قابل بیان می‌شود — **اما**:

- این دقیقاً **Source of Truth دوم** می‌سازد که `OQ-05 = 3A` و دستور صریح مالک پروژه («نباید Source of Truth دوم ساخته شود») آن را ممنوع کرده است؛
- باید با هر درج/به‌روزرسانی/ابطال هم‌گام شود → دوباره همان مسابقهٔ زمانی؛
- هیچ شاهد Repositoryای آن را توجیه نمی‌کند (`performance_records.total_weight_completed` صریحاً Snapshot **دوره‌ای** است، نه حالت جاری).

→ **رد بدون نیاز به تصمیم مالک پروژه** (نقض تصمیم قفل‌شده).

## ۹. `H-2` — معناشناسی Rollback و `DEC-018`

### ۹.۱ رفتار واقعی Laravel (تأییدشده از ساختار Repository)

```text

   └── آخرین Batch را میگیرد، مهاجرتهای آن را به ترتیب نزولی نام اجرا میکند
       └── هر مهاجرت: runDown()  →  down()
           └── اگر down() استثنا بدهد: استثنا به بالا منتشر میشود
               ⛔ حلقه همانجا متوقف میشود
               ⛔ ردیف مهاجرت ناموفق در جدول migrations باقی میماند
               ⛔ مهاجرتهای باقیماندهٔ همان Batch هرگز اجرا نمیشوند
```

**شاهد مستقیم محیط:**

```text

```

یعنی Batch بعدی (`[2]`) **فقط** مهاجرتهای V1.8 خواهد بود؛ خطر این یافته **متوجه تاریخچهٔ موجود نیست**.

### ۹.۲ سناریوی دقیق شکست

```text

   M-09  ✅ down شد
   M-08  ✅ down شد
   M-07  ❌ throw  →  فرمان متوقف شد
   M-06 … M-01  ⛔ اجرا نشدند

اجرای دوم:  M-09/M-08 دیگر در Batch نیستند → مستقیم M-07 → دوباره throw
   ⛔ M-06 … M-01 عملاً از مسیر migrate:rollback غیرقابلدسترس میشوند
   ⛔ (migrate:reset هم همان مسیر را طی میکند و در M-07 متوقف میشود)
```

**نتیجه:** ادعای `V1.8_DETAILED_SCHEMA_DESIGN.md §۱۲.۲` که «`--step=9` ترتیب معکوس را خودکار رعایت می‌کند» **نیمی درست است**: ترتیب معکوس رعایت می‌شود، اما **ادامه‌دادن پس از یک `down()` ناموفق رخ نمی‌دهد**. ادعا نادرست است.

### ۹.۳ تحلیل گزینه‌ها

| گزینه | محتوا | Rollback safety | Rollback convenience | Data preservation | Operational recovery |
|---|---|---|---|---|---|
| **A** | حفظ `throw` بدون تغییر | ✅ عالی (هرگز دادهٔ جعلی نمی‌سازد) | 🔴 بد — `M-06..M-01` غیرقابل‌دسترس | ✅ عالی | 🟠 نیازمند دخالت دستی: حذف ردیف `M-07` از جدول `migrations` |
| **B** | `down()` صریحاً «برگشت‌ناپذیر» اعلام شود + رویهٔ دستی مستند (اجرای دستی `SET NOT NULL` + حذف ردیف `migrations`) | ✅ عالی | 🟠 همچنان دستی | ✅ عالی | ✅ شفاف و مستند |
| **C** | **تفکیک Batch:** `M-07` در یک Batch **قدیمی‌تر** و مستقل از هشت مهاجرت دیگر اجرا شود | ✅ عالی | ✅ **`M-01..M-06`, `M-08`, `M-09` با یک `migrate:rollback` معمولی برمی‌گردند** | ✅ عالی | ✅ رویهٔ روشن: rollback اول = هشت مهاجرت · rollback دوم = `M-07` (که آگاهانه throw می‌کند) |

**آیا اجرای اول `M-07` بی‌خطر است؟** ✅ بله — §۹.۱ سند Schema صریحاً می‌گوید `M-07` **هیچ وابستگی ساختاری** ندارد (نه FK می‌سازد، نه ستون). تنها جهت آن `DROP NOT NULL` روی `tasks.weight` است که هیچ جدول دیگری به آن وابسته نیست.

### ۹.۵ پیادهٔ پیشنهادی گزینهٔ D (نوشته‌شده، اجرا نشده)

```php
public function down(): void
{
    $nullCount = DB::table('tasks')->whereNull('weight')->count();

    if ($nullCount > 0) {
        throw new RuntimeException(
            "M-07 cannot be safely rolled back: {$nullCount} task row(s) have weight = NULL "
            . 'and no reliable original value can be reconstructed. '
            . 'Decide manually before restoring NOT NULL.'
        );
    }

    DB::statement('ALTER TABLE tasks ALTER COLUMN weight SET NOT NULL');
}
```

**آیا این `DEC-018` را نقض می‌کند؟** ❌ **نه.** `DEC-018` دو چیز را ممنوع کرده است: (۱) تولید دادهٔ مصنوعی (`UPDATE … SET weight = 0`)، (۲) `down()` خالی/no-op. گزینهٔ D **هیچ‌کدام** را انجام نمی‌دهد: وقتی داده وجود ندارد، `SET NOT NULL` **بازیابی وضعیت قبلی** است، نه جعل داده؛ و وقتی داده وجود دارد، **همان `throw` آگاهانه** رخ می‌دهد. با این حال چون این یک **تغییر رفتار نسبت به متنِ مصوب `DEC-018`** است، **نیازمند تأیید صریح مالک پروژه** است.

## ۱۰. `H-3` — ساخت Module و قاعدهٔ `SUM = 100`

### ۱۰.۱ مسئلهٔ فنی (تأییدشده از متن تابع §۶.۱)

```sql
SELECT COUNT(*), COALESCE(SUM(weight), 0)
  INTO v_count, v_total
  FROM modules
 WHERE project_id = v_project_id AND deleted_at IS NULL;

IF v_count > 0 AND v_total <> 100.00 THEN RAISE EXCEPTION … END IF;
```

Trigger از نوع `AFTER INSERT OR UPDATE OR DELETE … DEFERRABLE INITIALLY DEFERRED FOR EACH ROW` است، پس بررسی در **`COMMIT`** انجام می‌شود.

### ۱۰.۲ تحلیل حالت‌به‌حالت

| سناریو | حالت میانی داخل تراکنش | وضعیت در `COMMIT` | نتیجه |
|---|---|---|---|
| Project تازه، **صفر** ماژول | — | `count = 0` → گارد عبور می‌کند | ✅ مشروع |
| Project تازه، **یک** ماژول با وزن ۴۰ | `count=1, total=40` | `count>0` و `total ≠ 100` → **خطا** | ❌ **ممکن نیست** |
| Project تازه، **یک** ماژول با وزن **۱۰۰** | `count=1, total=100` | عبور | ✅ ممکن (و تنها حالت تک‌ماژولیِ ممکن) |
| A=40, B=35, C=25 — **هر سه در یک تراکنش** | حالت‌های میانی: `40`، `75`، `100` | `count=3, total=100` → عبور | ✅ **ممکن** |
| A=40 و B=35 در یک تراکنش، C=25 در تراکنش دوم | تراکنش ۱: `count=2, total=75` | ❌ خطا در `COMMIT` اول | ❌ **ممکن نیست** |
| بازتوازن A: 40→45 و B: 35→30 در **یک** تراکنش | `105` سپس `100` | عبور | ✅ ممکن |
| بازتوازن A و B در **دو** تراکنش | تراکنش ۱: `105` | ❌ خطا | ❌ ممکن نیست |

**نتیجهٔ قطعی:** قاعدهٔ `SUM = 100` یک **invariant مرز-تراکنش** است، نه یک invariant سطح-دستور. سند §۶.۱ همین نتیجه را برای **بازتوازن** گرفته، اما صریحاً نگفته که **ایجاد تدریجی ماژول نیز غیرممکن است** و **قاعدهٔ «همه در یک تراکنش» را به‌عنوان الزام ثبت نکرده**. این یک شکاف مستنداتی/عملیاتی واقعی است.

### ۱۰.۳ یافتهٔ جدید `N-2` — بدنهٔ تابع Trigger معتبر نیست

```sql
v_project_id := COALESCE(NEW.project_id, OLD.project_id);
```

در Trigger **ردیفی** PL/pgSQL:

- برای `INSERT`: `OLD` **تخصیص نیافته** است؛
- برای `DELETE`: `NEW` **تخصیص نیافته** است؛
- ارجاع به ستون یک رکورد تخصیص‌نیافته در PL/pgSQL خطا می‌دهد:
  ```text
  ERROR: record "new" is not assigned yet
  DETAIL: The tuple structure of a not-yet-assigned record is indeterminate.
  ```

چون `COALESCE` هر دو استدلال را **ارزیابی می‌کند**، فرم فعلی برای `INSERT` (که `OLD` لازم دارد) و برای `DELETE` (که `NEW` لازم دارد) **خطا** می‌دهد. شکل صحیح باید بر `TG_OP` شاخه‌بندی کند:

```sql
IF (TG_OP = 'DELETE') THEN
    v_project_id := OLD.project_id;
ELSE
    v_project_id := NEW.project_id;
END IF;
```

همین الگو در `assert_module_stage_weight_sum()` (§۶.۲) که با `module_id` کار می‌کند نیز تکرار شده است.

> **محدودیت اعتبارسنجی:** این یافته **تحلیل ایستا** روی متن تابع است و **با اجرا تأیید نشده** — تأیید اجرایی، ساخت یک Trigger و اجرای `INSERT`/`DELETE` لازم دارد که در این فاز ممنوع است (`DDL`).

**شدت:** 🟠 HIGH — بدون اصلاح، `M-08` روی `INSERT` و `DELETE` ماژول **خطا** می‌دهد، نه فقط در حالت نامعتبر.

## ۱۱. `H-4` — Write Skew در تراکنش‌های همزمان

### ۱۱.۱ مسئله

```text
تراکنش A:  Module A 40 → 65   و   Module B 35 → 10      (مجموع هر دو: 75 → 75)
تراکنش B:  Module A 40 → 20   و   Module B 35 → 15      …
```

برای اثبات وجود شکاف، باید سناریویی ساخت که **هر تراکنش به‌تنهایی درست باشد ولی نتیجهٔ نهایی ناسازگار**:

```text
وضعیت اولیه:   A=40 · B=35 · C=25 · D=10    (مجموع = 110 → فرض کنید = 100 اصلاح شود)
وضعیت اولیه (معتبر): A=40 · B=35 · C=15 · D=10    (مجموع = 100)

تراکنش T1 (ردیفهای A و B):
   A: 40 → 65   B: 35 → 10
   دیدِ خودِ T1:  65 + 10 + C(15) + D(10) = 100  →  ✅ بررسی COMMIT عبور میکند

تراکنش T2 (ردیفهای C و D) — همزمان، بدون هیچ تضاد ردیفی:
   C: 15 → 40   D: 10 → 10 … (مثال: C: 15→45, D: 10→0? مقادیر باید >0 باشند)
   T2: C: 15 → 55 , D: 10 → 10  … دیدِ T2: A(40) + B(35) + 55 + 10 = 140 ≠ 100 → رد
```

مدل دقیق‌تر: T2 که فقط C و D را می‌بیند، برای رسیدن به ۱۰۰ در دیدِ خود باید `C + D = 100 − A − B = 25`. پس T2 مقادیر `C + D` را روی **۲۵** تنظیم می‌کند (تغییری نمیدهد یا بازتوزیع میکند). T1 مقادیر `A + B` را روی **۶۵** تنظیم می‌کند و `C + D` را **۳۵** می‌بیند.

```text
نتیجهٔ نهایی (ادغام نوشتهها):  A+B = 65  و  C+D = 25  →  مجموع = 90 ≠ 100  ❌
```

هر دو تراکنش در لحظهٔ `COMMIT` خودشان **سبز** بودند، چون هرکدام فقط **تصویر لحظه‌ای خود** را جمع زده‌اند. این **کلاسیک‌ترین شکل Write Skew** است: دو تراکنش روی مجموعه‌ردیف‌های **مجزا** می‌نویسند، پس هیچ قفل ردیفی بین‌شان رخ نمی‌دهد.

### ۱۱.۲ تحلیل سطح-انزوا

| سطح | اسنپ‌شات | آیا Skew را می‌بندد؟ | توضیح |
|---|---|---|---|
| `READ COMMITTED` (پیش‌فرض PostgreSQL) | به‌ازای هر دستور | ❌ **نه** | Trigger تعویق‌شده در پایان تراکنش اجرا می‌شود، اما هر تراکنش فقط **نوشته‌های خودش + دادهٔ کامیت‌شدهٔ قبلی** را می‌بیند. ردیف‌های مجزا هیچ تضادی تولید نمی‌کنند |
| `REPEATABLE READ` | یک اسنپ‌شات در شروع | ❌ **نه** | بدتر: تصویر **کهنه** است؛ و چون ردیف‌ها مجزا هستند، خطای 40001 هم رخ نمی‌دهد |
| `SERIALIZABLE` | یک اسنپ‌شات + SSI | ✅ **بله** | ساختار خطرناک (rw-antidependency) تشخیص داده می‌شود و یکی از تراکنش‌ها با `40001` شکست می‌خورد — **اما** نیازمند منطق Retry در اپلیکیشن است |
| قفل ردیف والد (`projects` / `modules` / `module_stages` `FOR UPDATE`) | — | ✅ **بله، قطعی** | همهٔ نویسندگان **یک محدودهٔ تجمیعی** روی یک شیء قفل واحد سریال می‌شوند → حالت میانیِ ناسازگار نمی‌تواند همزمان ساخته شود (`H-1` همان راهبرد) |
| قفل مشورتی (`pg_advisory_xact_lock`) | — | ✅ بله | همان تضمین، با شفافیت کمتر (به `H-1` گزینهٔ C) |

### ۱۱.۳ نتیجه‌گیری کلیدی

> **Trigger تعویق‌شده — هرچقدر هم درست نوشته شود — تراکنش‌های همزمان را سریالایز نمی‌کند.**
> اگر طراحی روی Trigger تکیه کند و قفل والد را «اختیاری» بداند، **یک حفرهٔ همزمانی واقعی** باقی می‌ماند.

### ۱۱.۴ دکترین پیشنهادی (کلید حل `H-1` + `H-4` + `H-3`)

```text
قاعدهٔ واحد پیشنهادی:
  «هر تراکنشی که ردیفهای زیر یک محدودهٔ تجمیعی را تغییر میدهد،
    باید نخست ردیف والدِ همان محدوده را قفل کند.»

  محدودهٔ تجمیع                     والدِ قابلقفل
  ────────────────────────────     ───────────────────────────────
  SUM(modules.weight) پروژه         projects.id
  SUM(module_stages.weight) ماژول    modules.id
  SUM(approved) یک Stage             module_stages.id           ← H-1
```

مزایا: یک قاعدهٔ واحد و قابل‌آموزش · هم‌خوان با الگوی موجود `lockForUpdate()` · بدون `SERIALIZABLE` و بدون Retry · قابل تست · و **قابل بازرسی** (قفل‌ها در مدل عادی قفل دیتابیس دیده می‌شوند، برخلاف قفل مشورتی).

**هزینه:** تراکنش‌های نوشتنِ همزمان روی **یک پروژه** سریال می‌شوند. حجم عملیات وزن‌دهی کم است، پس هزینهٔ عملی پذیرفتنی است. قفل `projects.id` یک قفل واحد به‌ازای هر پروژه است — بدون گلوگاه سراسری.


## ۱۲. `H-5` — Soft Delete و قاعدهٔ `= 100`

### ۱۲.۱ رفتار واقعی طراحی (تأییدشده از متن تابع §۶.۱)

```sql
FROM modules WHERE project_id = v_project_id AND deleted_at IS NULL;
IF v_count > 0 AND v_total <> 100.00 THEN RAISE EXCEPTION …
```

پس قاعدهٔ واقعی چنین است: **«مجموع وزن ماژول‌های حذف‌نشدهٔ یک پروژه یا صفر ماژول است، یا دقیقاً ۱۰۰»**.

### ۱۲.۲ سناریوهای مشخص

```text
وضعیت: A=40 · B=35 · C=25

(الف) Soft Delete فقط C (بدون بازتوازن) — در یک تراکنش
      پس از حذف: count = 2 , total = 75
      COMMIT → Trigger:  count>0 و total≠100  →  ❌ RAISE EXCEPTION
      نتیجه: حذف یک ماژول «بهتنهایی» ممنوع است؛
             باید در همان تراکنش خواهرها بازتوازن شوند (40→53.33… عملاً 40+60)
      ✅ رفتار ایمن — مغایرتی با سند §۵.۲ («Soft Delete ماژول با بازتوازن همراه») ندارد

(ب) Soft Delete هر سه ماژول (همه)
      count = 0  →  گارد عبور میکند  →  ✅ COMMIT موفق
      نتیجه: پروژه با «صفر ماژول فعال» باقی میماند

(ج) Restore ماژول C پس از آنکه خواهرها به ۱۰۰ بازتوازن شدهاند
      مثال: A=60 · B=40 (active) · C=25 (deleted) → Restore C
      پس از Restore: total = 60 + 40 + 25 = 125 , count = 3
      COMMIT → ❌ RAISE EXCEPTION
      نتیجه: Restore در همان تراکنش نیازمند بازتوازن است — نه یک عملیات تک‌کلیکی

(د) حذف فیزیکی ماژول
      FKهای فرزند (module_stages, stage_progress_approvals, tasks.module_id) همگی RESTRICT
      → DELETE فیزیکی خطا میدهد  → امنیت تاریخچه حفظ میشود
      ✅ مستقل از Trigger
```

### ۱۲.۳ آیا «صفر ماژول» یک حفره است؟

بله و نه — بستگی به تعریف کسب‌وکاری دارد:

| تفسیر | معنا | نتیجه |
|---|---|---|
| **الف) وضعیت «صفر ماژول» مشروع است** | پروژه تازه‌ساخته هنوز ماژول ندارد؛ همچنین پروژهای که همهٔ ماژولهایش آرشیو شده‌اند | ✅ **الزامی** — بدون این، `H-3` حل نمی‌شود (پروژه باید بتواند با صفر ماژول آغاز شود) · هزینه: می‌توان با Soft Delete همه، از قاعده «فرار» کرد |
| **ب) «صفر ماژول» فقط برای پروژهٔ تازه مشروع است** | پروژهای که هرگز ماژول نداشته، آزاد است؛ پروژهای که یک بار ماژول داشته، باید همیشه ≥۱ ماژول فعال داشته باشد | ⚠️ نیازمند یک وضعیت کندوکاوشده («آیا پروژه هرگز ماژول داشته؟») → پیچیدگی واقعی + نیازمند ستون یا کوئری تاریخی |
| **ج) «صفر ماژول» ممنوع است** | همیشه باید حداقل یک ماژول فعال با وزن ۱۰۰ باشد | ❌ **با `H-3` ناسازگار است** — Project نمیتواند ساخته شود |

### ۱۲.۴ توصیهٔ فنی

```text
RECOMMENDATION — NOT APPROVED
```

**توصیه: تفسیر (الف) با یک قید صریح.**

```text
قاعدهٔ پیشنهادی:
  • invariant روی مجموعهٔ ماژولهای «حذفنشده» (deleted_at IS NULL) اعمال میشود.
  • «صفر ماژول فعال» یک وضعیت مشروع است (و برای H-3 ضروری).
  • Soft Delete و Restore هر دو الزاماً در همان تراکنش بازتوازن میشوند (R-4).
  • هیچ قاعدهای برای «پروژهای که قبلاً ماژول داشته» ساخته نشود — چون نیازمند
    وضعیت/ستون جدید است و هیچ سندی آن را نخواسته.
```

**جایگزین اگر مالک پروژه (ب) را ترجیح دهد:** نیازمند یک فیلد وضعیت پروژه (`modules_state`: `none` \| `active`) — **یک قاعدهٔ کسب‌وکاری جدید که از خودمان اختراع نشد** و در این سند فقط به‌عنوان گزینه گزارش می‌شود.

**آیا `projects` خودش Soft Delete دارد؟** ✅ بله (`2026_09_17_140143_create_projects_table.php` → `softDeletesTz()`). **اما** طراحی §۴.۷ می‌گوید `projects` بدون تغییر ساختاری می‌ماند و Trigger روی `modules` است — پس Soft Delete یک **پروژه**، Trigger ماژول‌ها را فعال نمی‌کند و ماژول‌های آن پروژه در همان وضعیت می‌مانند. این رفتار **تصمیم‌گیری نشده** است. توصیه: این مورد در تصمیم `H-5` **صریحاً** پوشش داده شود (مثلاً «Soft Delete پروژه، invariant ماژول‌ها را تعلیق می‌کند» یا برعکس) — **قابل موکول** است چون در V1.8 هیچ مسیر کدی برای Soft Delete پروژه وجود ندارد.

**هیچ Constraint/Trigger/ستونی اضافه نشد.**

## ۱۴.۵ یافته‌های جدید کشف‌شده در همین بازبینی (`N-1`..`N-5`)

### `N-1` 🟠 — تناقض درونی مدل `supersede` با Immutability و سقف ظرفیت

**مشاهده از متن طراحی:**

```text
§۴.۳ status ∈ { pending | approved | rejected | superseded }
§۴.۳ chk_spa_decided_consistency:
        status <> 'pending'  ⇒  approved_amount IS NOT NULL
                            AND final_approved_by IS NOT NULL
                            AND decided_at IS NOT NULL
§۶.۴ trg_spa_immutable (BEFORE UPDATE):
        IF OLD.status <> 'pending' THEN RAISE EXCEPTION …
§۶.۵ سقف:  SUM(approved_amount) WHERE status = 'approved'
§۴.۳ supersedes_approval_id: «اصلاح رکورد قبلی (بدون بازنویسی)»
```

**تناقض:**

| پرسش | پاسخ طراحی | مشکل |
|---|---|---|
| یک رکورد `approved` چطور به `superseded` تبدیل می‌شود؟ | باید `status` آن `UPDATE` شود | ⛔ `trg_spa_immutable` **هر `UPDATE` روی رکورد غیر-`pending` را رد می‌کند** → گذار `approved → superseded` **غیرقابل اجرا** است |
| اگر رکورد قبلی `approved` بماند و فقط رکورد جدید `supersedes_approval_id` داشته باشد؟ | — | ⛔ سقف `SUM(...) WHERE status='approved'` **هر دو رکورد را جمع می‌زند** → **دوباره‌شماری** و رد شدن اصلاحِ موجه (`StageProgressCapacityExceededException` نادرست) |
| اگر رکورد جدید **مستقیماً با `status='superseded'`** درج شود؟ | — | ⚠️ با `chk_spa_decided_consistency` سازگار است (فیلدهای تصمیم پر می‌شوند) اما **معنای رویداد را خراب می‌کند**: یک «ابطال» به‌عنوان درج ثبت می‌شود و در گزارش‌های `status='approved'` هرگز دیده نمی‌شود |

**نتیجه:** مدل اصلاح (correction) در `stage_progress_approvals` **امروز منسجم نیست**. این یافته در بازبینی Migration Review کشف نشده بود.

**دو راه‌حل منسجم (هیچ‌کدام انتخاب نشد):**

| گزینه | محتوا | پیامد |
|---|---|---|
| **الف) گذار صریح مجاز شود** | `trg_spa_immutable` تنها گذار `approved|rejected → superseded` را **اجازه** دهد؛ سقف روی `status='approved'` بماند | ساده · اما یک استثنا در Trigger تغییرناپذیری وارد می‌کند (تاریخچه بازنویسی می‌شود، فقط با مقدار `status`) |
| **ب) سقف «فعال‌ها» را بشمارد** | منطق سقف به شکل زیر تغییر کند: `SUM(approved_amount)` روی رکوردهای `status='approved'` **که توسط هیچ رکورد دیگری ارجاع نشده‌اند** (`NOT EXISTS (SELECT 1 FROM stage_progress_approvals s WHERE s.supersedes_approval_id = spa.id)`)؛ Trigger تغییرناپذیری کاملاً سخت بماند | ✅ تاریخچه **هرگز بازنویسی نمی‌شود** · هزینه: کوئری سقف پیچیده‌تر می‌شود (و باید در **همان قفل والد `H-1`** اجرا شود) |

**توصیه (NOT APPROVED):** گزینهٔ **ب** — با دکترین «هیچ رکورد تاریخی بازنویسی نمی‌شود» (`BD-04` + Immutability) سازگارتر است. نیازمند تصمیم مالک پروژه نیست، **اما** چون معنای «تأیید تجمعی» را تعریف می‌کند، **باید پیش از `M-03`/`M-08` تثبیت شود.**

### `N-2` 🟠 — بدنهٔ تابع Trigger تجمعی برای `INSERT`/`DELETE` خطا می‌دهد

(تحلیل کامل در §۱۰.۳.) اصلاح: شاخه‌بندی بر `TG_OP`. **تحلیل ایستا — با اجرا تأیید نشده (DDL ممنوع).**

### `N-3` 🟡 — `tasks.module_id` / `module_stage_id` می‌توانند اشاره‌گر «پروژهٔ دیگر» باشند

```text
tasks.project_id           → projects.id        (NOT NULL)
tasks.module_id            → modules.id         (NULL)
tasks.module_stage_id      → module_stages.id   (NULL)

طراحی §۶.۶ فقط تضمین میکند:   tasks.module_id = module_stages.module_id  (برای Stage دادهشده)
هیچ چیزی تضمین نمیکند:        modules.project_id = tasks.project_id
هیچ چیزی تضمین نمی‌کند:        module_stages.module_id به همان پروژه تعلق دارد
```

**پیامد:** تسکی از پروژهٔ X می‌تواند به Stage ماژولی از پروژهٔ Y متصل شود و هیچ CHECK/Trigger این را نمی‌گیرد. **شدت 🟡 MEDIUM** — Service می‌تواند آن را ببندد، اما هیچ سندی این الزام را ثبت نکرده است.

**توصیه (NOT APPROVED):** افزودن یک قاعدهٔ صریح Service («Stage فقط از همان پروژهٔ تسک قابل انتخاب است») به `§۶.۶` — **بدون** Constraint جدید (نیازمند cross-table است). اگر `OQ-30` گزینهٔ B/D را تأیید کند، همین Trigger تک‌ردیفی می‌تواند این مورد را هم پوشش دهد (با یک lookup) — **تصمیم مالک پروژه**.

### `N-4` 🟡 — تنش دکترین: قواعد در Service یا در Database؟

| سند | گفته |
|---|---|
| `docs/10-database-design.md §۱` (جدول اصول) | «قواعد کسب‌وکاری | در لایه Application/Service — **نه** در Database» |
| `docs/V1.8_DETAILED_SCHEMA_DESIGN.md §۶` | ۵ `CONSTRAINT TRIGGER` + ۲ Trigger اختیاری |
| Repository | **صفر Trigger** — همهٔ CHECKهای موجود تک‌ردیفی هستند |

**نتیجه:** V1.8 در عمل دکترین مکتوب را تغییر می‌دهد، اما هیچ سندی این تفکیک را **صریح** نکرده است. خطر واقعی: نویسندهٔ بعدی نمی‌داند کدام قاعده «Service-only» و کدام «DB-enforced» است → همان شکافی که `C-06`/`C-07` را ساخت.

**توصیه (NOT APPROVED):** یک جدول واحد در سند Schema: «۱۴ قاعدهٔ تک‌ردیفی → DB؛ قواعد تجمعی → Service + (Trigger اختیاری Backstop)؛ قواعد cross-table → Service». **تصمیم مالک پروژه لازم است** چون دکترین را تعریف می‌کند.
