## ۴. T-5 — تحلیل تصمیم Project Soft-Delete

**شواهد پایدار:** `Project` از `SoftDeletes` استفاده می‌کند اما **هیچ مسیر حذف در کد وجود ندارد** (نه route، نه controller، نه service). Hard delete در DB با `RESTRICT` روی هر سه فرزند (`tasks`/`modules`/`wbs_phases`) مسدود است. هیچ DEC/BD ای قاعدهٔ حذف/restore Project را تعریف نکرده.

### گزینهٔ A — حذف Project اصلاً قابلیت محصول نیست

- **پیامد کسب‌وکار:** پاک‌سازی Project از طریق فرایند بیرون از سیستم انجام می‌شود؛ حذف/بایگانی فقط یک راه رسمی وجود دارد: پایان قرارداد (contract_id UNIQUE).
- **درستی داده:** حداکثر — هیچ مسیر حذف، هیچ invariant جدید.
- **Restore:** N/A.
- **تغییرات لازم:** **تست-فقط** (تست ثابت می‌کند مسیر حذف وجود ندارد و RESTRICT عمل می‌کند) یا حتی **هیچ تغییری**.
- **Migration:** NO. **UI/API:** NO.

### گزینهٔ B — حذف نرم فقط بدون Module فعال

- **پیامد کسب‌وکار:** حذف نرم فقط برای پروژه‌های «تمیز» مجاز؛ پروژهٔ دارای کار فعال باید ابتدا Moduleها را بایگانی کند (`ModuleService::archive` — الگوی موجود با invariant `SUM=100` و `DEC-024`).
- **درستی داده:** سالم — هیچ ماژولِ فعالِ یتیم.
- **Restore:** سرراست (همهٔ فرزندان سالم مانده‌اند).
- **گزارش‌ها:** نیازمند فیلتر `deleted_at IS NULL` در queryهای Project (بررسی در پیاده‌سازی).
- **تغییرات لازم:** سرویس حذف نرم جدید (یا action در controller) + گارد «ماژول فعال» + route + تست. **Migration: NO** (SoftDeletes از قبل روی مدل و ستون موجود است).
- **هزینه:** متوسط.

### گزینهٔ C — حذف نرم حتی با Module فعال، فرزندان دست‌نخورده

- **پیامد کسب‌وکار:** بایگانی سطح-پروژه؛ کارتابل/گزارش باید آگاهانه `deleted_at` را فیلتر کند وگرنه ماژول‌ها/تسک‌های پروژهٔ حذف‌شده همچنان در جریان کار دیده می‌شوند (اگرچه از طریق مسیر ناوبری Project قابل دسترسی نیستند).
- **درستی داده:** سالم در DB؛ **ریسک ناسازگاری معنایی** در queryهای فرزند که join مستقیم دارند.
- **Restore:** یک‌مرحله‌ای اما پیامدهای گزارشی دارد.
- **تغییرات لازم:** مشابه B ولی بدون گارد «ماژول فعال»؛ به‌علاوه حسابرسی queryهای گزارش‌گیری برای فیلتر حذف‌شده‌ها.
- **Migration:** NO. **هزینه:** متوسط-بالا (ریسک گزارش).

### گزینهٔ D — سایر (فقط با شواهد Repository)

هیچ شاهدی در Repository یافت نشد که سیاست دیگری را پشتیبانی کند (نه seeder، نه doc، نه DEC). **D فعلاً خالی است** مگر مالک قاعدهٔ جدیدی بدهد.

### 4.1 آنچه صرفاً مالک باید تعیین کند

1. آیا حذف/بایگانی Project اصلاً قابلیت محصول است؟ (A در برابر B/C)
2. اگر بله: Module فعال مسدود است یا نه؟
3. اگر بله: سیاست Restore چیست (چه کسی، چه زمانی)؟

```text
T-5 = OWNER DECISION REQUIRED / DEFERRED — بدون قاعدهٔ مالک، هیچ مسیر حذف ساخته نمی‌شود.
```

## ۶. T-1 — تحلیل بازگشایی (KEEP AS-IS در برابر M-10)

**invariant واقعی:** یک رکورد `stage_progress_approvals` می‌تواند حداکثر یک بار supersede شود — دو fork غیرمجاز است (`A→B` و `A→C` هم‌زمان).

| محور | ارزیابی |
|---|---|
| Enforcement فعلی | **Application-owned و کامل:** `assertNotSuperseded` در هر ۴ مسیر جهش‌دهنده (`supersede`/`adjust`/`approve`/`reject`) × ۵ فراخوانی — با تست رگرسیون (SupersedeChainTest) |
| ریسک bypass با SQL خام | ممکن است اگر اپراتور مستقیم روی DB بنویسد — ولی این ریسک «هر invariant application-owned» است، نه خاص این invariant |
| دسترسی عملیاتی/ادمین | هیچ مسیر ad-hoc SQL ای در خود محصول وجود ندارد؛ `tinker` فقط ابزار توسعه است |
| مالکیت درست | پروژه به‌طور عمدی invariantهای چرخه‌ای را Application-owned نگه داشته (`DEC-024`, `DEC-027`)؛ DB-owned کردن این یکی ناسازگار با معماری نیست ولی ** ضرورت عملی ندارد** |
| تداخل با معنای تاریخی | UNIQUE روی `supersedes_approval_id` با الگوی تاریخی سازگار است (NULL برای رکوردهای اول) — اما ** مزیت عملی نسبت به گارد فعلی ندارد** |
| Backfill / cleanup | **لازم نیست** — دادهٔ فعلی هیچ تکراری ندارد (کاتالوگ تأیید کرده) |
| Rollback / ریسک migration | M-10 روی `tms` اجرا می‌شد؛ ریسک عملیاتی واقعی (قفل‌گذاری کوتاه + تاریخچهٔ migration) بدون رفع نقص فعلی |
| نتیجهٔ خالص | محافظتِ ازدست‌رفته در برابر SQL خام — که خارج از مرزهای محصول است |
