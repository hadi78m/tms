## 6. Permission ≠ Business Rule

For every permission-gated operation, permission denial is terminal, but **permission alone never allows** — the chain continues:

- create: `create tasks` → project scope on `$data->project_id` → service invariants (stage-role rule if `module_stage_id` present).
- assign: `assign tasks` → project scope on the task's project → service guards (contractor scope on assignee, race protection, SLA).
- No permission exists for view/start/submit/dependencies → those operations' denials come from scope/contractor layers only.

Example: user lacking `create tasks` → DENY at policy, regardless of scope. User holding `create tasks` but scoped to other projects → DENY at scope. User holding permission + scoped → still subject to `TaskService` invariants (e.g. non-supervisor sending `module_stage_id` → `UnauthorizedTaskOperationException`).

## 9. Contractor Scope

- Canonical method: `TaskScopeService::assertCanAccess(Task, User)` → throws `ContractorScopeViolationException`. Identity: `users.contractor_id` non-null. Two other methods are Phase-S1 stubs (empty) — not touched.
- Invocation today: only `TaskAssignmentService` (assignee check). Controller/inline duplicates are actor-side copies of the same rule.
- Phase 1 disposition (no new contractor dimension, DEC-051 stays BLOCKED):
  - **Policy layer:** TaskPolicy abilities call the same actor-side contractor comparison (`$actor->contractor_id !== null && $task->contractor_id !== $actor->contractor_id` → deny) **by delegating to `TaskScopeService`** (new read-only method `canAccess(Task, User): bool` added next to `assertCanAccess`; `assertCanAccess` refactors to call it — behavior identical). The policy must not hand-roll a second copy of the comparison.
  - **Service guard:** unchanged — `TaskAssignmentService` keeps asserting contractor scope on the **assignee**.
  - Ordering evidence: today actor-side contractor check runs at controller (before service); assignee-side runs inside the service transaction. Target flow preserves this order (scope → policy(includes actor contractor) → controller → service(assignee contractor)). Documented as compliant with the mission's ordering template.
- index: contractor `whereHas('project', contractor_id)` filter stays as-is (query-level, additive with project scope).
