## 1) Executive Summary

V11-01 (Project Scope Authorization) هدفش اعمال مبنای scope تأییدشده است: **Supervisor = Assigned-based · Employer = Contract-based · Admin/Management = Unrestricted** (DEC-048)، با لایهٔ enforcement **G-C = Middleware + Policy + Service Guard** و **Query Scope** به‌عنوان مکانیزم پشتیبان.

یافته‌های قطعی این Design Gate:

1. **هیچ ساختار Project↔User در مخزن وجود ندارد** — نه pivot، نه ستون مالکیت، نه جدول generic assignment. نزدیک‌ترین قرینهٔ معماری `task_assignments` است که **در سطح Task** قفل شده (FK به `tasks`) و برای membership پروژه‌ای **قابل استفاده نیست**.
2. **Employer = Contract-based امروز قابل استقرار نیست** — زنجیرهٔ `Employer/User → Contract → Project` در مدل داده **ناقص** است: جدول `synced_contracts` هیچ `employer_id`/`user_id` ندارد و Employer فقط یک Spatie role بدون رابطهٔ هویتی است. این یک **Open Owner Decision** است (نه یک انتخاب مهندسی).
3. **Admin/Management عملاً الان unrestricted هستند** — چون هیچ project-scope‌ای در هیچ لایه وجود ندارد. طراحی باید «unrestricted» را به‌صورت **project-scope bypass** مدل کند، **نه** bypass مجوزدهی/invariants (DEC-050).
4. **لایهٔ Policy/Gate کاملاً غایب است** — صفر کلاس Policy، صفر `Gate::define`، فقط ۲ نقطهٔ `->can()`. بنابراین V11-01 به یک **زیرساخت** نیاز دارد که **پیش‌نیاز** ترتیب DEC-049 است (نه تغییر آن).
5. **ریسک مهاجرت بحرانی:** با اعمال scope، پروژه‌های موجود که هیچ تخصیص ناظری ندارند **بلافاصله برای ناظر غیرقابل‌دسترس** می‌شوند مگر strategy backfill تعیین شود. این **Open Owner Decision** است.

**نتیجه:** جهت معماری روشن است، اما **حداقل ۸ تصمیم Owner** پیش از هر Migration/پیاده‌سازی باقی است. این سند این تصمیم‌ها را سطح‌بندی و شفاف می‌کند.

### 4.5 الگوی مرجع درون-مخزن: `task_assignments` + `TaskAssignmentService`

قوی‌ترین قرینهٔ معماری برای H-C (و برای «یک تخصیص فعال») همین زوج است:

```text
TaskAssignmentService::assign():
  DB::transaction:
    Task::where(id)->lockForUpdate()->firstOrFail()
    $this->scopeService->assertCanAccess(...)          // domain scope guard
    $activeAssignment = $task->activeAssignment()->lockForUpdate()->first()
    if same user → idempotent return
    if $activeAssignment → ended_at = now() + audit task_unassigned   // پایان، نه حذف
    create new assignment
  → QueryException ⇒ TaskAssignmentRaceConditionException (بک‌استاپ DB)
──────
DB: idx_active_assignment UNIQUE (task_id) WHERE ended_at IS NULL      // حداکثر یک فعال
    chk_ta_dates CHECK (ended_at IS NULL OR ended_at >= assigned_at)
```

یافته: الگو **تاریخی** است (`assigned_at`/`ended_at` · ردیف قبلی حفظ می‌شود · `reason` · audit)، «فعال» **مشتق** است (`ended_at IS NULL`)، و یکپارچگی «حداکثر یک فعال» هم در **Service** و هم با **partial unique index** تضمین می‌شود.

> این **evidence** است، نه تصمیم. نام جدول/ستون‌های نهایی H-C توسط Owner تعیین نشده و در §16 فهرست شده است.

## 5) Membership Design Options

> ✅ **تصمیم مالک (2026-09-28): `M-1 — Generic Project Membership / Assignment`** (جزئیات ثبت: Recon §18.2 · تحت DEC-048). گزینه‌های زیر به‌عنوان **recon options** حفظ شده‌اند؛ انتخاب M-1 انجام شده و بازگشایی نمی‌شود. نام نهایی جدول/ستون‌ها/ایندکس ⇒ دروازهٔ Design/Implementation.

**یافتهٔ قطعی:** هیچ ساختار موجودی نمی‌تواند به‌عنوان Project Membership استفاده شود:
- `task_assignments` FK به `tasks` دارد ⇒ **سطح Task**، نه Project. (گزینهٔ H-E در recon = invalid.)
- `users.contractor_id` یک رابطهٔ **کاربر→شرکت** است، نه کاربر→پروژه.
- `projects` فقط `contract_id`/`contractor_id` دارد؛ هیچ ستون مالکیت کاربری ندارد.
- `synced_contracts` هیچ رابطهٔ Employer/User ندارد.
- هیچ جدول generic assignment/membership دیگری در ۳۲ migration وجود ندارد.

⇒ **ساختار جدید (Migration) الزامی است** (این قبلاً در recon و DEC-048 نیز تأیید شده).

| g | audit trail علاوه بر تاریخ membership؟ | بله (`activity_logs` با رویداد `project_membership_*`) | ⏳ **باز (non-blocking — دروازهٔ پیاده‌سازی)** — توصیه مهندسی: بله |

> نکتهٔ سازگاری: **soft delete نباید جایگزین `ended_at` شود** — چون soft delete رکورد را از queryهای پیش‌فرض پنهان می‌کند و با الزام «تخصیص قبلی باید قابل‌دسترسی تاریخی بماند» در تنش است. اگر soft delete انتخاب شود، باید سیاست نمایش تاریخی صریح باشد.

## 6) Supervisor Cardinality Design («حداکثر یک Supervisor فعال در هر Project»)

### 6.1 معنای «فعال»

دو تعریف repository-compatible (بدون انتخاب):

| تعریف | مبنا | Effect |
|---|---|---|
| **مشتق** | `ended_at IS NULL` | مطابق `task_assignments`/`activeAssignment`؛ صفر ستون اضافه؛ حقیقت واحد |
| **ذخیره‌شده** | boolean `is_active` + CHECK consistency با `ended_at` | خواندن ساده‌تر، ولی دو منبع حقیقت ⇒ خطر drift |

قرینهٔ درون-مخزن به‌سمت **مشتق** است (`Task::activeAssignment()` ، `scopeActive()` برای approvals). تصمیم نهایی = Owner ⇒ ✅ **DECIDED (2026-09-28): مشتق — `ended_at IS NULL`** (OD-6-a؛ صفر `is_active` · صفر `status`).

### 6.2 مکانیزم‌های enforcement (مقایسه)

| گزینه | مکانیزم | تضمین در رقابت (race) | سازگاری با مخزن | ملاحظه |
|---|---|---|---|---|
| **C-1 — Service validation تنها** | در transaction: پایان دادن به فعال قبلی + ایجاد جدید | ضعیف (بدون unique، دو transaction هم‌زمان می‌توانند عبور کنند) | قرینهٔ «فقط یکی pending» (OQ-06/DEC-010) در Service پیاده شده | ریسک race؛ قرینهٔ `TaskAssignmentRaceConditionException` نشان می‌دهد پروژه به race حساس است |
| **C-2 — Partial unique index** | `CREATE UNIQUE INDEX ... ON (project_id) WHERE ended_at IS NULL [AND position='supervisor']` | **قوی** (در سطح DB) | **دقیقاً** الگوی `idx_active_assignment` | نیازمند تصمیم دربارهٔ predicate (اگر جدول generic باشد، باید با `position` محدود شود) |
| **C-3 — Exclusion constraint (btree_gist)** | ممنوعیت هم‌پوشانی بازه‌ها با `daterange`/`tstzrange` | قوی برای «بازه‌های ناهم‌پوشان» | **قرینه ندارد** | قاعدهٔ Owner «یک ناظر فعال» است، **نه** «بازه‌ها نباید هم‌پوشانی داشته باشند» (تخصیص آینده‌نگر مجاز است). احتمالاً **over-engineering** — flagging، نه پیشنهاد |
| **C-4 — ترکیب C-2 + C-1** | partial unique index به‌عنوان بک‌استاپ DB + Service برای پایان دادن/جایگزینی/audit | قوی‌ترین | دقیقاً همان الگوی `task_assignments` + `TaskAssignmentService` | نسخهٔ QueryException در Service به exception دامنه نگاشت شود |

> **تصمیم ثبت‌شدهٔ مرتبط:** فقط **قاعدهٔ کاردینالیتی** (حداکثر یک Supervisor فعال) و **الزام جایگزینی** (OD-6-d) تصمیم مالک‌اند. **مکانیزم دقیق** (C-1..C-4 · predicate ایندکس ‌یکتا) در **دروازهٔ پیاده‌سازی** تعیین و اجرا می‌شود — هنوز پیاده‌سازی نشده. (ركورد C-3 همچنان قرینه‌ندارد؛ ذكر آن از باب مقایسه است.)

### 6.3 رفتار جایگزینی (مطابق مثال Owner)

```text
Project X
  A: 01/01/2026 → 30/06/2026   (ended_at = 30/06/2026)   ← historical، حذف نمی‌شود
  B: 01/07/2026 → NULL                                  ← active (ended_at IS NULL)
```

ترتیب عملیات پیشنهادی (منطبق با الگوی TaskAssignmentService):

```text
DB::transaction:
  Project::where(id)->lockForUpdate()
  active = membership(project_id, position=supervisor, ended_at IS NULL)->lockForUpdate()->first()
  if active && active.user_id === new_user → idempotent (no-op)
  if active → active.ended_at = now(); save(); audit membership_ended
  create new membership(project_id, user_id, started_at = now(), ended_at = NULL); audit membership_started
  QueryException ⇒ ProjectMembershipRaceCondition(Exception)   // بک‌استاپ partial unique index
```

نکات مبهم در زمان recon و **وضعیت تصمیم آن‌ها (2026-09-28)**:

- ✅ **نوع بازه = `timestampTz`** (OD-6-b).
- ✅ **تخصیص آینده‌نگر در V1.11 پشتیبانی نمی‌شود** (OD-6-c) ⇒ predicate `ended_at IS NULL` کافی می‌ماند؛ زمان‌محور کردن لازم نیست.
- ✅ **سیاست پایان هنگام جایگزینی = پایان دادن به تخصیص فعال قبلی** (OD-6-d)؛ جزئیات `now()`/`lockForUpdate`/ایندکس ⇒ دروازهٔ پیاده‌سازی.
- ⏳ **باز (non-blocking):** اجباری/اختیاری بودن `reason`/`assigned_by` ⇒ دروازهٔ پیاده‌سازی.

## 7) Employer Scope Design (Contract-based)

**یافتهٔ قطعی:** زنجیرهٔ `Employer/User → Contract → Project` در مخزن **ناقص** است.

| حلقه | وجود | Evidence |
|---|:-:|---|
| Contract → Project | **بله** (`projects.contract_id` unique) | `create_projects_table.php:14` |
| User → Employer identity | **خیر** — Employer فقط Spatie role است (بدون ستون/جدول identity) | `InitialTmsSeeder:34`؛ zero `employer_id` در schema |
| Contract → Employer/User | **خیر** — `synced_contracts` فقط `contractor_id` دارد | `create_synced_contracts_table.php:17-18` |
| User → Contractor | بله (`users.contractor_id`) — ولی **Contractor ≠ Employer** | `create_users_table.php:23` · recon Part D |

⇒ **حلقهٔ گمشده = Employer ↔ Contract (یا Employer ↔ User-identity).** بدون تعریف آن، «Employer = Contract-based» **قابل استقرار نیست**.

### 7.1 گزینه‌های ممکن (بدون انتخاب)

| گزینه | توضیح | ملاحظه |
|---|---|---|
| **E-1 — Membership پروژه‌ای برای Employer (M-1)** | Employer هم از طریق همان ساختار H-C به project(های) contract تخصیص داده می‌شود | سازگار با M-1؛ ولی «Contract-based» را به «Assignment-based» تبدیل می‌کند ⇒ requires Owner confirmation that this still satisfies the approved semantics |
| **E-2 — جدول/link در سطح Contract** | رابطهٔ Employer↔Contract (مثلاً `contract_memberships` یا ستون `employer_user_id`) | نزدیک‌تر به معنای «Contract-based»؛ Migration جداگانه؛ دامنهٔ بزرگ‌تر |
| **E-3 — اشتقاق از پیمانکار قرارداد** | Employer scope از `synced_contracts.contractor_id` مشتق شود | **شک**: Employer به‌طور مفهومی ≠ Contractor؛ این با تفکیک تأییدشدهٔ recon در تنش است ⇒ صرفاً جهت اطلاع، نه پیشنهاد |
| **E-4 — موکول موقت** | تا حل لینک، Employer در حالت فعلی (بدون project-scope) بماند | نقض کوتاه‌مدت «Employer = Contract-based»؛ نیازمند تأیید صریح Owner |

> **این انتخاب مالک است، نه مهندس.** به‌عنوان OD-2 در §16 ثبت شده است. ⇒ ✅ **تصمیم مالک (2026-09-28): `E-4 — Employer Scope DEFERRED`** (تفصیل: Recon §18.3): قاعدهٔ «Employer = Contract-based» حفظ می‌شود، اما **صفر اختراع هویت Employer · صفر `employer_id` · صفر استنتاج از Contractor · صفر استفاده از نقش Spatie به‌عنوان هویت DB · صفر تغییر `synced_contracts`**. Employer-scope تا طراحی/تأیید رابطهٔ واقعی Employer↔Contract **DEFERRED** است و **V11-01 منتظر آن نمی‌ماند**؛ مسیر اصلی روی **Supervisor scope** متمرکز می‌ماند.

## 8) Admin / Management Scope Design (Unrestricted)

**یافته:** Admin (۱۱ permission) و Management (`view reports`/`export reports`) **الان unrestricted عملی** هستند — چون هیچ project-filter ای در هیچ لایه وجود ندارد که باید bypass شود (`TaskController::index` فقط contractor-scope دارد؛ `ModuleController::index` و `TaskController::create` از `Project::all()`/unfiltered استفاده می‌کنند).

نکتهٔ کلیدی (مطابق DEC-050): «unrestricted» باید **فقط** به‌معنای **project-scope bypass** باشد، **نه** bypass سه چیز دیگر:

```text
Unrestricted  ⇒  Project Scope = ALL projects (coarse scope bypass)
Unrestricted  ⇏  bypass Permission          (دقیقاً همان چیزی که قبلاً بر اساس role تأیید شده)
Unrestricted  ⇏  bypass Business Invariants (final approval · stage lock · SUM=100 · ceiling …)
Unrestricted  ⇏  مرز مالی
```

پیاده‌سازی repository-compatible: در لایهٔ Policy، یک قاعدهٔ scope-evaluator که برای نقش‌های admin/management مقدار «همهٔ پروژه‌ها» را برمی‌گرداند **بدون** آن‌که `authorize()` را کاملاً دور بزند. هیچ `Gate::before` در مخزن وجود ندارد؛ اگر افزوده شود، باید **فقط** scope را bypass کند و invariants دست‌نخورده بمانند.

**Open:** معنای دقیق «unrestricted» (خواندنی در برابر همهٔ اقدامات نوشتنی) و اینکه آیا Management (که فقط `view reports` دارد) باید scope پروژه‌ای داشته باشد یا نه — OD-3 و OD-4 در §16.

## 11) Permission Integration (DEC-050 — `Permission ≠ Project Scope`)

مدل قفل‌شده: `User → Role` · `Role → Permission` · `User → Direct Permission` · effective = Role + Direct · **Grant-only · صفر Deny** · کاتالوگ سیستم‌کنترل · **صفر Dynamic Permission→Route mapping**.

### 11.1 نمونهٔ مفهومی الزامی (بدون پیاده‌سازی)

```text
User U:
  Permission: tasks.update                      ✅
  Project Membership: project X  →  supervisor   ✅
  Project Membership: project Y  →  ندارد        ❌

Task T_X ∈ project X   ⇒ Policy: permission ✅ AND scope ✅  ⇒ ALLOW
Task T_Y ∈ project Y   ⇒ Policy: permission ✅ AND scope ❌  ⇒ DENY   (403/404)
```

**چرا DENY؟** چون Policy = `Permission + Project Scope + Resource relationship`. permission به‌تنهایی **برای یک منبع project-scoped کافی نیست** (DEC-048 بند ۳.۲). این دقیقاً همان چیزی است که از نشت «permission به‌عنوان کلید همه‌چیز» جلوگیری می‌کند.

### 11.2 مرزها (الزام)

| قاعده | توضیح |
|---|---|
| Permission نباید scope را بدهد | داشتن `tasks.update` دسترسی به پروژه‌های دیگر نمی‌دهد |
| Permission نباید scope را override کند | هیچ `Gate::before`/مسیر خاصی مجاز نیست scope را دور بزند مگر برای admin/management آن هم **فقط** به‌عنوان scope bypass |
| Permission نباید invariants را override کند | final approval · stage lock · SUM=100 · ceiling بدون تغییر |
| Scope نباید جای Permission را بگیرد | انتساب به پروژه مجوز اقدام نمی‌دهد؛ هر دو لازم است |
| Direct permission Grant-only | صفر Deny؛ صفر permission منفی |
| کاتالوگ سیستم‌کنترل | صفر ساخت permission از UI؛ صفر dynamic route mapping |

> **سازگاری با DEC-050:** نقش/position در membership پروژه‌ای (اگر M-1 انتخاب شود) باید صرفاً یک **برچسب عملیاتی scope** باشد و **نباید** به یک سیستم Permission موازی تبدیل شود.

## 12) Historical Access Model

اصل مالک (DEC-051 + DEC-048): وقتی یک تخصیص/قرارداد پایان می‌یابد، **دادهٔ تاریخی نباید غیرقابل‌دسترسی شود**.

اما تمایز حیاتی:

```text
Historical visibility        ≠     Current operational authorization
─────────────────────────────────────────────────────────────────────
رکورد قدیمی باقی می‌ماند            دسترسی عملیاتی فعلی فقط برای تخصیص فعال
و برای audit/reporting              (ended_at IS NULL)
قابل استعلام است
```

### 12.1 سناریوها

| سناریو | انتظار تاریخی | انتظار عملیاتی | وضعیت طراحی |
|---|---|---|---|
| **پایان تخصیص ناظر** | ردیف `A` با `ended_at` حفظ می‌شود؛ audit/گزارش تاریخی قابل استعلام | ناظر `A` دیگر scope عملیاتی پروژه `X` را ندارد؛ ناظر `B` فعال است | مبنا روشن؛ **جزئیات نمایش تاریخی = OD-7** |
| **پایان قرارداد Employer** | پروژه/task/approval تاریخی حفظ می‌شود | Employer دیگر scope عملیاتی ندارد | **وابسته به حل E-2 (لینک Employer↔Contract) — OD-2** |
| **پایان قرارداد Contractor** | دادهٔ تاریخی حفظ می‌شود (گاردریل DEC-051) | Contractor scope فعلی حفظ می‌شود (بدون بُعد جدید) | **صفر تغییر در V11-01** (DEC-051 = NO-OP) |

### 12.2 پرسش‌های باز (نباید اختراع شوند)

- آیا یک ناظرِ تاریخی (assignment پایان‌یافته) باید پروژه را **بخواند** (read-only تاریخی) یا هیچ‌گونه دسترسی نداشته باشد؟
- آیا «بازخوانی تاریخی» باید از مسیر Reports/Audit (system-wide) تأمین شود یا از scope عملیاتی جدا بماند؟
- معنای «historical/audit/reporting where applicable» در DEC-048 نیازمند تفسیر عملیاتی است ⇒ **OD-7**.

## 14) Test Design (فقط ماتریس — هیچ تستی نوشته نمی‌شود)

| گروه | سناریو | انتظار |
|---|---|---|
| **Supervisor — scope** | ناظرِ تخصیص‌یافته به پروژهٔ X به منبع X دسترسی دارد | ALLOW |
| | ناظرِ بدون تخصیص به پروژهٔ Y به منبع Y دسترسی ندارد | 403/404 |
| | ناظرِ تاریخی (assignment پایان‌یافته) scope عملیاتی ندارد | DENY (operational) |
| | رکورد تخصیص پایان‌یافته حفظ می‌شود | موجودی در DB (query تاریخی) |
| **Cardinality** | تلاش برای ایجاد ناظر فعال دوم روی همان پروژه | رد در Service و/یا DB |
| | جایگزینی ناظر: A پایان، B فعال؛ A تاریخی می‌ماند | ردیف A حفظ + `ended_at` |
| | هم‌زمانی: دو درخواست جایگزینی موازی | یکی موفق؛ دیگری race/exception؛ صفر دو ناظر فعال |
| **Employer** | Employer کاربر مرتبط با قرارداد پروژهٔ X به X دسترسی دارد | ALLOW — **مسدود تا OD-2** |
| | Employer به پروژهٔ بی‌ربط دسترسی ندارد | DENY/403 |
| **Admin/Management** | Admin/Management scope محدود نمی‌شوند | ALLOW در همهٔ پروژه‌ها |
| | invariants همچنان اجرا می‌شوند (final approval/stage lock/SUM=100) | invariant exception، نه bypass |
| **Permission** | permission بدون scope ⇒ DENY | 403/404 |
| | scope بدون permission ⇒ DENY | 403 |
| | permission + scope ⇒ ALLOW | 200 |
| **Service Guard** | Policy مجوز دارد اما invariant نقض می‌شود (مثلاً stage پس از final approval) | invariant exception |
| **Query Scope** | لیست‌ها فقط منابع پروژه‌های مجاز را برمی‌گردانند | صفر leakage |
| | ذخیره/به‌روزرسانی مستقیم رکورد غیرمجاز (IDOR) | DENY |
| **Regression** | contractor isolation موجود حفظ می‌شود | تست‌های موجود سبز |
| | مسیرهای عادی (۲۹۰ تست موجود) بدون تغییر | سبز |
| | system-wide بودن Reports/Audit حفظ می‌شود (مگر OD-5) | سبز |

**پیش‌نیاز زیرساخت تست:** هر تست Policy باید یک fixture تخصیص پروژه‌ای بسازد؛ بنابراین تست‌ها پس از Migration ساختار membership نوشته می‌شوند (نه قبل).
